# Узкие места и как их закрыть до написания кода

Ревью 2026-09-06 по решениям частей 1–11. Каждое место: что ломается,
что делаем в архитектуре, каким тестом ловим.

## 1. Канал «роль → движок»

**Риск.** MCP-сервер в каждой сессии, JSON-RPC к движку по сокету,
идентификация по `AOE_SESSION_ID`: три непроверенных звена (наследование
переменной в Claude и Codex, порядок старта движка и сессий, живой сокет в
момент вызова). Отказ любого — роль не может сдать ход.

**Решение.** Убрать MCP и сокет из первой версии. Сигнал — файл.

- Идентификация — по каталогу, а не по окружению: одна рабочая копия
  принадлежит ровно одной задаче, и в ней лежит `.orch/<task>/current.json`
  (шаг, заход, сессия), который движок переписывает перед каждым промптом.
  Команда `orch`, запущенная ролью в рабочей копии, находит задачу по
  `git rev-parse --show-toplevel`. Переменные окружения на сессию AoE
  даёт только песочницам (`src/session/builder.rs:795`), поэтому на них
  не опираемся; `AOE_SESSION_ID` из окружения агента — только сверка.
- В сессиях доступна команда `orch` (тот же пакет). Роль завершает ход
  командой `orch done clean`. Команда читает цепочку и базу только для
  чтения, проверяет исход и наличие артефакта, печатает понятную ошибку
  или пишет `signals/<step>-<run>.json` атомарно (запись во временный файл
  и переименование). Никакой связи с живым движком.
- Движок читает файл сигнала **только когда ход закончился** (сессия в
  `Idle`), поэтому роль, вызвавшая `orch done` и продолжившая править
  файлы, ничего не сломает: следующий шаг не стартует, пока она работает.
- Если команда недоступна, роль пишет тот же JSON руками — формат в
  промпте, одна строка.

**Тесты.** `orch done` с неверным исходом → ненулевой код и текст с
допустимыми исходами; без артефакта → отказ с путём; вне рабочей копии
задачи → отказ «вызван не из задачи». Интеграционный: роль Claude и роль
Codex запускают `orch whoami` и получают задачу и шаг.

## 2. Узнать, что ход кончился

**Риск.** WebSocket рвётся, событие `Stopped` пропущено, задача висит
навсегда. Или событие приходит от чужого хода (агент разбудил себя сам).

**Решение.** Источник истины — опрос `GET /api/sessions` раз в 5 секунд,
он идемпотентен: «шаг едет, сессия `Idle`, сигнал есть → переход; сигнал
нет → красный». WebSocket в первой версии не используем вовсе, 5 секунд
задержки не важны. Ролям запрещены `ScheduleWakeup` и `Monitor`
(промпт), а движок при `Idle` без сигнала всё равно ничего не додумывает.

**Тесты.** Движок против поддельного AoE: последовательность статусов
`Running → Idle` с файлом сигнала и без; `Idle` пришёл дважды → переход
один; статус `Waiting` (вопрос) → задача «ждёт ответа», ничего не
двигается.

## 3. Переход применился дважды или наполовину

**Риск.** Двойной клик по кнопке, сигнал и кнопка в одну секунду,
падение движка между записью в базу и созданием сессии.

**Решение.** У задачи есть номер ревизии. Каждая кнопка в панели несёт
ревизию, на которой её нарисовали; движок принимает движение только с
текущей ревизией, иначе молча перерисовывает панель. Все движения —
одна транзакция: «записать переход» и «записать намерение создать
сессию». Исполнение намерения (создать сессию, послать промпт) отдельно
и повторяемо: после падения движок находит намерения без результата и
доводит их; создание сессии идёт с `idempotency_key = задача/шаг/заход`,
поэтому повтор не рождает вторую сессию.

**Тесты.** Два клика с одной ревизией → одно движение. Сигнал и кнопка →
применяется первое, второе отклонено с записью в журнал. Убить движок
после транзакции, до создания сессии → после старта сессия создана
ровно одна.

## 4. Восстановление после перезапуска

**Риск.** После рестарта демона движок видит сессии в состоянии
`resuming`, ход мог кончиться пока нас не было, сессия могла исчезнуть.

**Решение.** На старте один проход сверки по каждой идущей задаче:
сессия есть и `Running` → ждём; `Idle` → обычная обработка по п. 2;
`Stopped`/нет воркера → послать промпт «продолжай», он будит воркер;
сессии нет → задача «брошена», красный. Сверка та же, что обычный опрос,
отдельного кода нет.

**Тесты.** Снимок базы «шаг едет» + поддельный AoE в каждом из четырёх
состояний → ожидаемое действие. Живой: перезапуск `aoe serve` посреди
хода Conventions, задача доезжает.

## 5. Файлы задачи

**Риск.** Подмена каталога артефактов AoE ссылкой — трюк на внутреннем
поведении, ломается любым обновлением.

**Решение.** Папка задачи в рабочей копии: `.orch/T12/`, исключена из
git локально. Роли пишут родными инструментами, веб AoE открывает файлы
рабочей копии штатно. Путь лежит в `ORCH_DIR` и в индексе базы. Трюк с
ссылкой не делаем. Пропажа папки при удалении ветки — приемлемая цена,
сессии с транскриптами остаются.

**Тесты.** Проверка артефакта по индексу: файл на месте / нет / пустой.

## 6. Создание сессии и рабочая копия

**Риск.** Промпт послан, пока сессия ещё создаётся; вторая сессия задачи
не подключилась к тому же каталогу; удаление сессии унесло рабочую
копию.

**Решение.** Создание с `?wait=ready`; промпт с повтором до трёх раз при
`session_transient`. Первая сессия задачи — `create_new_branch: true`,
следующие — `create_new_branch: false` с той же веткой, движок сверяет
`project_path` ответа с путём первой и падает громко при расхождении.
Сессии никогда не удаляются движком, только архив.

**Тесты.** Интеграционный: две сессии одной ветки → один `project_path`.

## 7. Сборка промпта

**Риск.** Роль со сброшенной памятью получает не то или не всё: не тот
заход, чужие комментарии, устаревший список файлов.

**Решение.** Сборка — чистая функция от (цепочка, шаг, состояние задачи
из базы, файлы). Комментарии владельца — только адресованные этому
шагу и ещё не доставленные; доставка помечается в той же транзакции,
что создание намерения промпта.

**Тесты.** Снимки собранного промпта для сценариев: первый заход,
второй заход после возврата с комментарием, автономный режим,
`continue` вместо `fresh`.

## 8. Панель и кнопка у поля ввода

**Риск.** Чтение черновика плагином (`composer.read`) не сработает или
сработает не на всех устройствах; предел 64 КиБ на панель.

**Решение.** Проверяется в спайке до всего остального. Запасной путь:
комментарий — обычное сообщение текущей роли со словами «для следующего
шага: …», роль вызывает `orch note "<текст>"`; хуже, но работает. Панель
задач показывает не больше 30 задач и обрезает пути.

**Тесты.** Живой: клик по кнопке приходит воркеру с `session_id`; текст
из поля приходит в параметрах.

## 9. Автономный режим и вопросы

**Риск.** Автоответ на вопрос роли выбирает не тот вариант; вопрос с
несколькими частями или свободным полем.

**Решение.** Первая линия — промпт: в автономной задаче вопросов не
задавать. Автоответ — страховка: по каждой части вопроса вариант с
пометкой «(рекомендую)», иначе первый; свободные поля пустые; выбор
записывается в журнал задачи и в панель. Если ответ отклонён — задача
встаёт красной, автономия не «любой ценой».

**Тесты.** Записанные полезные нагрузки вопросов Claude → ожидаемый ответ.

## 10. Файл цепочки

**Риск.** Опечатка в `next`, `moves` на несуществующий шаг, цикл без
выхода, шаг без пути к концу — всплывает на живой задаче.

**Решение.** Линтер при загрузке и в тестах: все цели существуют, из
каждого шага достижим `done`, у ворот есть `moves`, исходы не
дублируются, `max_runs` ≥ 1. Ошибка загрузки — задача не создаётся, текст
ошибки в панели и в CLI.

**Тесты.** Линтер на всех файлах `chains/` в CI; отрицательные файлы с
каждой ошибкой.

## 11. Codex

**Риск.** Второй агент проверен хуже: режим полных прав называется
иначе, наследование окружения и возможность запускать `orch` не
доказаны.

**Решение.** Карта режимов по агентам в одном месте кода. Первый прогон
Conventions намеренно с одним шагом на Codex.

**Тесты.** Интеграционный п. 1 для Codex.

## 12. Режим «только чтение» (`mode: plan`)

**Риск.** В этом режиме роль не может ни писать файл, ни, вероятно,
запускать `orch done`: сдать ход нечем.

**Решение.** Не в первой версии. Поле `run.mode` принимает только `full`,
`plan` отклоняется линтером с пояснением. Вернуть после спайка: если
`plan` пропускает наш CLI — включить; если нет — сдача через последнее
сообщение роли (движок пишет его в файл артефакта, последняя строка —
исход).

## 13. Стоимость и зацикливание внутри хода

**Риск.** Роль крутится внутри одного хода час.

**Решение.** Сторож AoE плюс ваша кнопка Stop. Отдельного предела
времени в первой версии нет; журнал задачи показывает длительность
каждого хода, чтобы решить, нужен ли он.

## Дополнено разбором 24 вопросов

Ответы и принятые решения — `PLAN.md` §13; главные для кода: порядок записи
файлов задачи до создания сессии, `orch push` вместо git-хуков, лист
автономии на задачу вместо режима, очередь `max_running`, пресеты в цепочке,
подагентам передаётся текст роли, а не путь.

## Что ещё упростить в первой версии

1. **Без MCP и сокета**: CLI `orch` в сессии + файл сигнала + окружение.
2. **Без WebSocket**: опрос статусов раз в 5 секунд.
3. **Без подмены каталога**: папка задачи в рабочей копии.
4. **Без `mode: plan`** до спайка.
5. **Панель минимальная**: список задач на главном, панель задачи в
   сессии, кнопка у поля ввода. Бейджи и колонки в сайдбаре позже.
6. **Одна цепочка первой**: Conventions целиком в трёх режимах
   автономии, потом Deep.
7. **Одно правило записи**: любое изменение задачи — транзакция в базе
   с ревизией; исполнение снаружи (AoE) всегда повторяемо по намерению.

## Спайк перед кодом, в порядке важности

1. `orch`-скрипт из PATH запускается ролью Claude и ролью Codex в
   рабочей копии и находит задачу по каталогу.
2. `POST /api/sessions` → `Idle` после хода виден в `GET /api/sessions`;
   промпт в `Idle` и в уснувшую сессию доставляется.
3. Две сессии на одной ветке — один каталог.
4. Плагин из шаблона: панель с кнопкой, клик приходит; `composer.read`
   отдаёт текст.
5. Вопрос `AskUserQuestion` висит два часа — ничего его не гасит;
   ответ через API `elicitations` принимается.
6. `mode: plan` пропускает ли `orch done` (решает п. 12).

Проверки 1, 2, 3, 5, 6 идут против рабочего демона на 8065; проверка 4 —
против отдельного демона на 8199 с изолированным `XDG_CONFIG_HOME`
(`DECISIONS-NEEDED.md` п. 1). Тестовые сессии создаются в группе `orch-test` и
архивируются, ветки `t0-*` удаляются.

|---|---|---|

| 2 | конец хода в `GET /api/sessions`; промпт в `Idle` и в сессию без воркера | **ok** — доставлено во всех трёх случаях |

Что спайк изменил в коде и в решениях:

1. **`Idle` сразу после отправки промпта — не конец хода.** `POST /acp/prompt`
   возвращает `sent`, а статус сессии ещё несколько секунд остаётся прежним
   `Idle`. Движок, который читает статус в лоб, немедленно объявит «нет
   сигнала» и остановит задачу на ровном месте. Признак конца хода —
   `status == Idle` **и** `idle_entered_at` позже времени отправки промпта;
   `run.prompt_sent_at` для этого и нужен.
2. **Транскрипт приходит потоком по токенам.** Строки `replay?view=rows` бьют
   текст на куски («за», «да», «ча»), поэтому искать подстроку в отдельной
   строке бесполезно — сначала склеить.
3. **Воркер плагина запирает сам себя**, если обрабатывает клик в том же
   потоке, где читает ответы хоста: `ui.state.set` внутри обработчика ждёт
   ответа, который может прийти только через занятый поток чтения. Входящие
   вызовы обрабатываются отдельным потоком.
4. **`config.get` читает по одному ключу** (`{"key": "poll_secs"}`), а не
   все настройки разом.
5. **Модели Claude называются `sonnet`, `opus[1m]`, `haiku`**
   (`GET /api/acp/option-catalog`), а не полными идентификаторами API.
   Цепочки уже написаны правильно; линтер значения моделей не проверяет,
   потому что каталог зависит от установленных адаптеров.
6. **Локально поставленный плагин не виден живому демону** до его
   перезапуска. Разработка панели идёт на отдельном демоне
   (`DECISIONS-NEEDED.md` п. 1).
7. **`mode: plan` подтверждён как непригодный** (п. 12 выше): роль в этом
   режиме не выполнила `orch done`, а составила план и встала в `Waiting` с
   просьбой выйти из режима планирования. Линтер продолжает отклонять
   `mode: plan`; возвращать нечего.
8. **Висящий вопрос не гасит ничто, кроме перезапуска демона.** Ни таймера,
   ни TTL: единственное место — `cancel_orphaned_elicitations`
   (`src/acp/supervisor.rs:3340`), которое снимает вопросы, осиротевшие после
   смерти прежнего демона. Измерено: вопрос провисел 73 минуты и остался в
   `Waiting`. Значит, таймер на человека движку не нужен (`PLAN.md` §2,
   правило 6), а после рестарта демона висевший вопрос превращается в
   обычное «нет сигнала».
9. **Ответ на вопрос принимается по API и ход продолжается**, но только пока
   жив процесс агента. Тот же вопрос, отвеченный через 73 минуты, дал
   `ElicitationResolved { outcome: Accepted }` и сразу `Stopped`: воркер к
   тому времени ушёл. Для движка это не особый случай — обычное «ход кончился
   без сигнала», уже описанное поведение. Форма вопроса в сыром транскрипте:
   события лежат под ключом `frames`, поля формы называются `question_0`,
   `question_0..N`, за каждым может идти свободное поле `question_<n>_custom`.
10. **Сессия, у которой сняли ветку, но оставили каталог worktree**, ломает
    следующее создание с той же веткой («Worktree already exists»). Уборка
    после прогона обязана снять замок, удалить каталог и только потом ветку —
    иначе полигон копит мусор, который всплывает через час.
