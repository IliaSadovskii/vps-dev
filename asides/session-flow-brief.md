# Разработка в одной сессии: чего хочет владелец и к чему пришли

Черновик от 2026-09-10. Свод разговора: задача, ограничения, найденное,
решённое, нерешённое. Пишется как вход для независимого разбора.

## 1. Кто и что делает

Владелец — программист с большим опытом. Архитектуру новой системы держит
в голове целиком: модули, бизнес-логика, желаемые паттерны, стек. Хочет
писать эту систему **сам, рядом с агентом**, а не поручать её.

Машина: `vps-dev` — сервер разработки, где живут проекты и агенты. Клиент —
Agent of Empires (AoE): сессия = один агент (Claude Code / Codex / Gemini CLI /
OpenCode) в одном каталоге. Поверх AoE владелец построил оркестратор (`orch/`)
с цепочками ролей.

## 2. Что не устроило в оркестраторе

- Цепочка из многих агентов проходит кучу итераций, роли «загоняются»,
  находят много лишнего, и потом PR разбирается два дня.
- Мелкую задачу через цепочку делать не быстрее, чем среднюю: ожидание съедает
  выигрыш. Отсюда соблазн пихать в одну цепочку побольше — а это ровно то,
  что делает PR неразбираемым.
- Вывод владельца: хочется работать **очень мелкими кусками** и проверять
  каждый самому.

Это не частная неудача. Тот же режим отказа описан снаружи: Cognition
(«Don't Build Multi-Agents», Walden Yan, опыт Devin) — разрыв контекста между
агентами есть корень ненадёжности, по умолчанию однопоточный линейный агент.
Их нынешняя продовая позиция: запись в код однопоточная, лишние агенты дают
мнение, а не действия. Плюс наблюдение из анализа 25 264 агентских PR: в 79 %
один и тот же человек и ревьюит, и переписывает вклад агента.

## 3. Чего владелец хочет

**Основной режим — одна сессия, мелкие срезы.**
Поговорили → зафиксировали решение → агент делает один кусок → PR → владелец
читает дифф (в AoE комментарии на диффе уходят агенту промптом) → следующий
кусок в той же сессии.

Требования к режиму:

1. Не повторять голосом одно и то же каждый раз — правила должны лежать
   в проекте и подтягиваться сами.
2. Агент **не должен додумывать** в дорогих местах (схема, контракт, новая
   зависимость) — обязан остановиться и спросить.
3. Разработка **вглубь, а не вширь**: сначала каркас и сквозные заботы, потом
   конкретные страницы и модули. Живой пример провала: попросил «построй
   фронт» для страницы прав — агент построил страницу, не подумав про layout,
   переиспользуемые компоненты, единый модуль уведомлений, общее хранение
   состояний загрузки, глобальную валидацию. То же и на бэке: сначала
   структура и разрезы, потом модуль.
4. Проект строится **с нуля**. Legacy-восстановление не интересует.
5. Качество и документированность обеспечиваются **механикой**, а не
   пожеланиями в промпте.
6. Работа в нескольких проектах → нужен **единый формат документации**, в том
   числе для уже начатых проектов со свалкой в `docs/`.
7. Мультипровайдерность: используются четыре агента, формат должен читаться
   всеми.

**Оркестратор не выбрасывается.** Роль разделяется:
- одна сессия — там, где владелец хочет читать каждый PR сам;
- оркестратор — задачи, где он готов доверить архитектурные решения агенту
  и не проверять лично.
Документация, правила и скелет должны работать **в обоих** режимах: в цепочке
на них ссылается и себя перепроверяет агент, в сессии проверяет владелец.

## 4. Что нашли: обзор подходов (сентябрь 2026)

### Тяжёлые конвейеры — не подходят, но есть что украсть
- **BMAD-METHOD** — ~49k звёзд, 12+ ролей, PRD и архитектура до кода.
  Минусы признают и сторонники: предписательность, освоение ~2 месяца,
  перебор на мелочах.
- **GSD (Get Shit Done)** — 50 md-файлов, 6 слэш-команд, 2 хука; цикл
  обсудить → исследовать → выполнить → проверить. Оригинал заархивирован
  26.06.2026, продолжение — Open GSD.
  **Идея, которую стоит взять:** исполнение фазы в **свежей сессии** с чистым
  контекстом, план передаётся файлом. Лечит «context rot» — деградацию
  к концу длинной сессии.
- **Superpowers** — владелец явно не хочет: спека, ревью, оркестрация внутри
  сессии.

### Спека как артефакт
- **Spec Kit** (GitHub) — greenfield, конституция + 7 команд, стопка плотных
  документов на фичу. Для мелких срезов перебор.
- **Kiro** (AWS, Claude через Bedrock) — requirements/design/tasks, `steering
  files` (постоянный системный промпт проекта), `hooks`, **Review mode**
  (агент предлагает, человек одобряет, потом код). Хвалят для greenfield.
  Минус: отдельная IDE, а работа идёт из AoE.
- **OpenSpec** — дельты `ADDED/MODIFIED/REMOVED` против `openspec/specs/`,
  цикл propose → apply → archive, слэш-команды `/opsx:*`, ставится
  `npm i -g @fission-ai/openspec` (Node ≥ 20.19), кладёт скиллы
  в `.claude/skills/`, `.agents/skills/`.
  **Вызывается человеком, не агентом** — это команда, а не автоматика.
  Важно: **brownfield-first**, а у владельца greenfield.
- **Tessl** — спека как исходник, код помечен `// GENERATED FROM SPEC`.
  В январе 2026 развернулись в «менеджер пакетов для скиллов». Обзоры:
  наблюдать, не внедрять.

### Опыт с OpenSpec: обе стороны
Плюсы (layandreas, kd05): заявленное ускорение 2-5x; онбординг за 30 минут
даёт стартовый набор спек по недокументированному коду; «структура без
бюрократии»; спеки — обычный markdown в репозитории; контекст не пропадает
между сессиями.

Минусы: ~2 млн токенов в день у одного автора; веток git не заводит;
`validate` иногда ложно ругается; **дрейф спеки** — главная жалоба, расходится
за дни; перебор на мелочах (багфикс → 4 user stories и 16 критериев приёмки);
эксперимент с редизайном фронта — 2 часа и много токенов впустую, автор ушёл
на простой `Instructions.md`.

### Критика SDD как класса
- HN, «Ask HN: What Happened to Spec-Driven Development?»: спека **не задаёт
  одну реализацию**; чтобы задавала — должна стать новым языком. Чем заменили:
  `plan.md` + петля проверки. Ирония: агенты изобретают фичи, которых не
  видно без чтения кода — спеки защищали ровно от этого, и их всё равно
  бросили.
- HN, «SDD: The Waterfall Strikes Back» (332 очка): к середине проекта спека —
  каша, мелкая правка требует сложных манипуляций. Что реально используют:
  куски ~100 строк, README и заметки о решениях, TDD-first, уточнение по ходу.
- Marmelab (Zaninotto, автор react-admin): против SDD целиком. Петля Lean:
  рискованное допущение → простейший эксперимент → агент → повтор. 3D-инструмент
  за 10 часов без спек, документация — короткие журналы сессий.
- Разрастание в команде: аудит через полгода — 41 файл спек в 9 репозиториях,
  описывающих один сервис по-разному, 9 вариантов `AGENTS.md`.
- Хабр, соло-разработчик, 25+ релизов без регрессий до пользователя: спека
  с секцией Gates внутри, ledger инвариантов, один фикс на релиз, каждая
  строка спеки проверяемая («Enter на non-URL → `#/scan` с предзаполненным
  фильтром»). Цена: 10-30 минут спеки на 5-20 минут работы агента; формально —
  всё разваливается. Повтор одного прогона дал 23 расхождения → для критичного
  писать псевдокод, а не описание.

### Проверка вместо описания
- **VSDD** — 7 фаз, 5 ворот, роли Архитектор/Строитель/Противник/Учётчик,
  формальная верификация (Kani, Dafny, TLA+), «Zero-Slop»: каждая строка кода
  прослеживается до требования. Целиком неподъёмно; ценен **принцип
  трассируемости**.
- **Acceptance-tests-first + EARS**: критерии приёмки в жёстком синтаксисе
  ложатся 1:1 на тест-кейсы. Формулировка из обсуждений: как только спека
  зафиксирована тестами, модель не может галлюцинировать. Это единственный
  найденный ответ на дрейф, кроме слова «дисциплина».

### Ворота вместо уговоров
- **Архитектурные fitness-функции**: ArchUnit (Java), dependency-cruiser (TS),
  eslint-plugin-boundaries, import-linter (Python). Стоят в CI, блокируют
  merge при деградации архитектурной характеристики. Оценка: при агентах это
  единственный надёжный способ удерживать правила на скорости генерации.
  Явление имеет имя — **AI architecture drift**. Инструментарий дозрел
  в Q1 2026 (Spring Modulith 1.4, ArchUnit 1.3, jMolecules).
- **Детектор копипасты** (jscpd и аналоги) с порогом в CI — копипаста
  становится измеримой, а не «на глаз».
- **Context Store** (InfoQ) — готовый синтез: машиночитаемые спеки +
  падающие тесты + fitness-функции в одном версионируемом хранилище рядом
  с кодом; слои: структура, происхождение, поведение, соответствие. Человек
  пишет спеки, пишет падающие тесты, определяет fitness-функции, решает, что
  не обсуждается. Ревью смещается с «что изменилось» на «почему». Тезис:
  код отгружается на машинной скорости, понимание вместе с ним — нет.

### Обучающаяся петля
- **Compound Engineering** (Every): план → работа → ревью → **compound**.
  Четвёртый шаг разбирает комментарии ревью, вытаскивает закономерности
  и дописывает правила в `CLAUDE.md`. Каждый баг → правило. Плагин под Claude
  Code, Cursor, Codex. Принцип: каждая фича делает следующую проще.

### Документация: стандарты
- **arc42** — 12 разделов. Прямо в тему: **§8 Cross-cutting Concepts** (это
  и есть «каркас»: логирование, аутентификация, обработка ошибок, доменная
  модель) и **§9 Architecture Decisions**. Прямое указание стандарта: не
  пытайтесь покрыть все темы, берите только нужные.
- **ADR / MADR** — решения датированы, не правятся, перекрываются новыми.
  Инструменты: adr-tools, log4brains.
- **C4** — диаграммы, 4 уровня, текстом (Structurizr DSL, PlantUML).
- **Diátaxis** — четыре типа доки (обучение / инструкция / справочник /
  объяснение), Django, Canonical, Cloudflare. Но это про **пользовательскую**
  документацию. Оттуда: не смешивать типы на странице; «компас, а не клетка».
- **AGENTS.md** — открытая спека с августа 2025 (OpenAI, Google, Cursor,
  Factory), в декабре 2025 передана Linux Foundation (Agentic AI Foundation,
  платиновые участники AWS, Anthropic, Block, Google, Microsoft, OpenAI).
  60 000+ проектов; читают Codex, Cursor, Devin, Gemini CLI, Copilot, VS Code,
  Amp, Jules. `CLAUDE.md` — симлинк.
- **SKILL.md / agentskills.io** — открытый стандарт с декабря 2025, ~40
  клиентов; тело до ~5k токенов; прогрессивное раскрытие: на старте видно имя
  и описание, тело грузится, когда описание подошло.
- **llms.txt** — оглавление для агентов; предложение, не стандарт, принятие
  смешанное. Полезная деталь: секция `## Optional` имеет договорную семантику
  «выкидывается первой при нехватке контекста».
- **RAD-AI** (arXiv) — проверено, **не подходит**: про документирование систем
  с ИИ внутри, а не про доку в разработке с агентом.

### Документация: что решает дрейф
- **Living Documentation** (Cyrille Martraire, Addison-Wesley) — теория ровно
  этой задачи: различение **стабильного и изменчивого знания** (требования
  стабильнее дизайн-решений; многое знание менее стабильно, чем кажется);
  **evergreen-документы с нулевой поддержкой**; не смешивать документацию
  стратегии с документацией реализации; организовывать артефакты вдоль
  стабильных осей; **генерировать из кода, а не писать руками**; разговор —
  тоже передача знания.
  Поправка под наш случай: книга писалась про людей и разрешает заменять
  документ разговором. Агент во вчерашнем разговоре не участвовал — доля
  записанного выше, но записывать надо только стабильное.
- **Memory Bank (Cline)** — готовый набор, копируется в проект. Шесть файлов
  в `memory-bank/` с иерархией зависимости, которая и есть деление по скорости
  устаревания:
  - стабильные: `projectbrief.md` (основа), `productContext.md`,
    `systemPatterns.md` (архитектура и паттерны), `techContext.md` (стек);
  - изменчивые: `activeContext.md` (текущий фокус, последние изменения) —
    после каждой сессии; `progress.md` (что работает, что осталось) — на вехах.
  Обновление: по команде «обнови memory bank» агент перечитывает **все** файлы;
  плюс при обнаружении нового паттерна или существенного изменения.
  Слабость (признана в его же документации): всё держится на аккуратности
  агента; расходятся файлы — ломается всё. Дрейф не решён, а переложен на
  агента. Разошёлся по другим клиентам (Roo Code и др.).
- **Регламент Red Hat** (июль 2026): `AGENTS.md` **до 150 строк** — установка,
  инструменты, тесты и где они, указатели на документы; **индексировать,
  а не дублировать**; писать только молчаливые инварианты и грабли проекта;
  убирать всё, что модель выведет сама; **автосгенерированные контекст-файлы
  вредят**, когда набиты общеизвестным; файл динамический — повторяющаяся
  ошибка агента фиксируется правилом.
- **Stack Overflow / O'Reilly** (март 2026): **эталонный файл-образец** —
  один реальный файл в репозитории, где все правила соблюдены сразу, плюс
  примеры «правильно / неправильно». Работает лучше прозы про
  переиспользуемость.
- **Инструменты против дрейфа**: инструментов, которые реально следят за кодом
  и ловят расхождение, **нет**. Работает другое — сделать документ производным
  артефактом одного источника и уронить CI, когда источник изменился, а
  производное нет. Существующее: Dredd (контракты API), Vale (линт прозы),
  AST-подход (drift-vscode), генерация доки и SDK из спеки (Fern).
- Про `CLAUDE.md`: держать до ~200 строк; модель надёжно держит ~150
  инструкций; расплывчатые правила не работают, работают конкретные.

## 5. К чему пришли (предварительно)

**Базовый минимум, с которого стартуем:**
1. `AGENTS.md` — правила: как здесь строят. `CLAUDE.md` — симлинк.
2. Тесты как приёмка: договорились о поведении → тест до кода.
3. Ворота в CI: тесты, линтер, границы модулей, детектор копипасты.
4. Привычка: один срез — один PR — владелец читает дифф.

Всё остальное — опции, добавляются по одной, когда упрёшься.

**Разделение двух осей (ключевое различение разговора):**
- «что система делает» — поведение; живёт в задаче и в тестах; при мелких
  срезах отдельная большая дока не нужна;
- «как здесь строят» — стек, инструменты, границы, правила; повторяется
  в каждой задаче, поэтому выносится один раз.
Это же разделение независимо сделали Kiro (specs vs steering) и Spec Kit
(spec vs constitution).

**Каркас — артефакт и два входа в него.**
Артефакт: короткая таблица сквозных забот со статусами
`построен (путь) / нужен, не построен / не нужен`, решение (пакет/подход),
правило использования. Первой строкой — парадигма (например: «структура по
домену, `app/Domain/<контекст>`, дефолтный Laravel-way не расширяем») — без
неё агент откатывается в дефолт фреймворка.

Список сквозных забот почти универсален:
- фронт: layout и навигация; маршрутизация и защита маршрутов; получение
  данных и кэш; формы и валидация; уведомления; состояния загрузки и ошибки;
  права на элементах; i18n; тема и токены;
- бэк: границы модулей; транзакции; ошибки наружу; авторизация; валидация
  входа; логи и трассировка; миграции; фоновые задачи; конфигурация.
Универсален список, не универсальна глубина.

Вход 1 — **разговор о каркасе** (команда, зовётся человеком): смотрит стек
и структуру, по типу приложения берёт список забот, по каждой решает — нужна
ли, свой код или пакет, какое правило; **ищет пакеты в интернете, а не
вспоминает**; спрашивает пачками по 4-6 с вариантами и пометкой «рекомендую»;
пишет таблицу и ADR. **Ничего не строит** — только решает и записывает.
Первый заход ограничен решениями, которые дорого менять потом. Нужен режим
повторного прохода: приложение приросло новым измерением — обновить.

Вход 2 — **рефлекс перед фичей** (всегда, без вызова): выпиши, какие заботы
задевает задача; если хоть одна «не построена» — стоп, скажи владельцу,
предложи сделать её первым PR; вторую реализацию существующего не создавай.
Выдать это списком **до кода**. Каркасный PR и фича — никогда в одном PR.

**Опросник при заведении проекта** — что должно попасть в `AGENTS.md`,
по убыванию частоты промахов агента:
1. как себя проверить (раннер, обязательный уровень тестов, одна команда,
   где логи, чем глянуть глазами — Playwright);
2. как поднять проект одной командой (на этой машине — `ports claim` /
   `ports run`);
3. **когда остановиться и спросить** (схема БД, публичный контракт, новая
   зависимость, необратимая миграция);
4. границы и структура: слои, направление зависимостей, куда кладётся новый
   код, что нельзя импортировать, чем это проверяется в CI;
5. стек и **чего не брать** (список нежелательного важнее желательного);
6. стиль решений: ORM или SQL, исключения или Result, DTO на границе,
   миграции;
7. линт и формат — одна команда с авто-фиксом;
8. git: ветки, размер PR, формат коммита;
9. несущее: что не трогать никогда; секреты и окружение.

Три требования к самому опроснику: спрашивать пачками, а не по одному;
**проверять то, что записал** (каждая команда из файла должна реально
запуститься при генерации); не «один раз перед стартом» — нужен режим
повторного прохода плюс дописывание строки после каждого промаха.

**Документация — четыре класса по сроку жизни.**
Устаревает только класс «описание текущего состояния». Правило не устаревает
(оно требует состояния, а не описывает). Решение не устаревает (датировано,
перекрывается новым). Поэтому класс «текущее состояние» надо сокращать:
что можно — в тесты и схемы, что нельзя — генерировать, остальное честно
пометить снимком с датой.

Предложенная раскладка (имена из arc42, принцип иерархии из Memory Bank):
```
AGENTS.md                       правила для агента (CLAUDE.md — симлинк)
docs/arc42/08-concepts.md       сквозные концепции = каркас
docs/arc42/09-decisions/        ADR в формате MADR
docs/arc42/03-context.md        контекст и границы — когда понадобится
docs/notes/                     снимки с датой, не поддерживаются
docs/README.md                  чему верить и в каком порядке
```
`docs/README.md` — три строки: правда это код и тесты; `08-concepts` говорит,
где что лежит; `09-decisions` объясняет почему; `notes/` — снимки на дату,
могут врать.

Единообразны слоты, не содержимое. Плюс **эталонный файл-образец** вместо
части правил.

Отдельная разовая команда для уже начатых проектов: инвентаризовать `docs/`,
разложить по слотам, предложить удалить лишнее, **проверить дешёвые
утверждения** (путь существует? команда запускается? пакет в зависимостях?),
отдать таблицу на утверждение, спорное — в `docs/notes/archive/` с датой.

**Мультипровайдерность:** тело команд — `SKILL.md` по открытому стандарту
в `.agents/skills/`, симлинки под каждого агента; `AGENTS.md` читают все.

**Если всё-таки брать OpenSpec — лайфхаки против его болячек:**
порог (спека только на структурное: контракт, схема, новый модуль);
не дублировать тест (поведение в тесте, спека — про намерение и решение;
дублирование и есть источник дрейфа); архив обязателен до merge, хуком;
сверка дельты с реально сделанным в конце среза; `openspec validate` в CI;
не заводить спеки на проект вперёд.

**Что забрать из оркестратора в любом случае:** промпты ролей → в скиллы;
копилку Наладчика (повторяющиеся огрехи) → в `AGENTS.md`; ворота цепочки →
в CI проекта.

## 6. Где не определились

1. **OpenSpec: брать или нет.** Аргументы за: контекст между сессиями, готовый
   цикл, онбординг legacy. Против: brownfield-first при greenfield-задаче,
   дрейф, перебор на мелочах, токены. Вариант «поставить на машину, в проект
   не заводить, вернуться через месяц по симптому „третий раз объясняю одно
   и то же“» — предварительный.
2. **Своя команда-опросник или чужой готовый набор** (Memory Bank целиком,
   его раскладка, регламент Red Hat).
3. **EARS для критериев приёмки** — вводить жёстко (1:1 в тесты) или писать
   свободно.
4. **Свежая сессия на исполнение** (идея из GSD) — встраивать сразу или
   сначала посмотреть, когда одна сессия начнёт «уставать».
5. **Сколько брать в первом заходе:** только ядро (правила + тесты + ворота);
   ядро + compound-петля; всё сразу.
6. **`project new`** — что кладёт: голый каркас, каркас со стендом,
   плюс `gh repo create`.
7. **Стек новой системы не назван** — от него зависят инструменты для
   fitness-функций, детектора копипасты и раннера тестов.

## 7. Как это встроить в vps-dev

Механизм в репозитории уже есть и подходит: роль `style` раздаёт
`/var/lib/vps-dev/style/` — общий промпт (порт 8071) плюс справки по одной
на тему (`machine/ports.md`, `browser.md`, `mail.md`, `limits.md`), которые
агент открывает только когда понадобилась. Это готовое прогрессивное
раскрытие, не хватает раздела не про машину, а про **метод работы**.

Наброски правок:
1. Роль `agents` — при желании доставить `openspec` (Node ≥ 20.19).
2. Роль `style` — раздел `/var/lib/vps-dev/style/work/`: как резать задачу,
   два режима (мелочь мимо спеки / структурное), ворота, правило проверяемых
   строк; строка-оглавление в общий промпт.
3. Команда `project` рядом с `ports` (роль `ports` держит бинарь в `files/`):
   `project new <имя>` — каталог в `/projects`, git init, скелет `AGENTS.md`,
   `docs/`, каркас проекта, `ports claim`.
4. Команда «привести доку к формату» для уже начатых проектов.
5. README — раздел «Как здесь ведут разработку»; оркестратор помечается как
   второй режим (не заморожен: он для задач, где владелец готов доверить
   архитектурные решения агенту).

Осторожно: справки в `style/work/` — это метод владельца, а не факты машины.
Написанные вперёд, они устареют или окажутся общими словами. Первая версия —
нарочито короткая, дописывается по промахам.
