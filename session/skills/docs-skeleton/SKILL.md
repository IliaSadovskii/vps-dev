# docs-skeleton

Каркас — решение, которое следующая фича будет вынуждена повторить. Сделал
один раз и ни на что не влияет — фича, не каркас. Твоя работа — записать,
что уже решено, спросить о верхнем уровне и оставить всё остальное
строками, к которым агент вернётся в задаче. Строить — не твоя работа,
решать мелочи заранее — тоже.

Прочитай перед началом, целиком:
- `../FORMAT.md` — что в какой файл, форма таблицы каркаса, сторож;
- `../PRINCIPLES.md` §5, §6, §7; `../asking.md`;
- в `../../sample/` — **только форма**: таблицы «Каркас» и «Тесты» в
  `AGENTS.md`, `docs/scenarios.md`, `docs/rules/frontend.md`,
  `docs/decisions/`. Содержимое образца не переносится.

Вход: `AGENTS.md` (после `docs-base`), код, `docs/`, `docs/scenarios.md`,
если есть. Репозиторий может быть занят — работай в отдельном worktree.

## Шаг 0. Сценарии

Нет `docs/scenarios.md` — заведи черновик: 5–8 сквозных проходов на
настоящих именах и числах, хотя бы один — где что-то идёт не так.
Источники: «Продукт», маршруты и страницы, документы. Неизвестные имена и
числа придумай правдоподобно с пометкой «(допущение)». Концовка — ответ
владельца: где не уверен, два варианта. Последняя строка сценария —
«Задевает: …», заполнишь на шаге 3. Есть файл — не переписывай, дописывай
недостающее.

## Шаг 1. Черновик таблицы — из кода и документов, до вопросов

Шесть осей по потоку работы, по каждой затравка; затравка — пол, не
потолок: прочитай продукт и сценарии, добавь заботы, которых нет в
затравке, но которые здесь повторятся.

| Ось | Затравка |
|---|---|
| Поверхность | лайаут и навигация; состояния экрана; формы и ошибки полей; списки, фильтры, сортировка; уведомления; подтверждение деструктивного; URL как состояние; адаптивность |
| Хранение | идентификаторы наружу; миграции; справочник против перечисления; сиды; файлы; мягкое удаление; история изменений |
| Обработка | границы модулей; действия; объекты данных на границе; значения с инвариантом; события домена; очереди |
| Выход | форма ответа и ошибок; письма; экспорт; внешний API и версия |
| Сквозное | права и область; транзакции; время и пояс; языки; настройки; конфигурация; журнал и персональные данные |
| Проверка | виды тестов и до чего каждый дотягивается |

Для каждой заботы: **образец** — путь, который надо повторять, или `—`;
**правило** — из `AGENTS.md`, кода, документов; **проверка** — тест,
скрипт или «ревью». Заботы, чьё правило уже в «Правилах», всё равно
получают строку — по ней агент называет заботу в предложении; правило в
строке — ссылка «см. Правила», без текста; путей в колонке «Правило» нет,
второй образец — отдельная строка.

Фильтр — «или»: повторится в каждой второй фиче **или** дорого переделать
(данные, права, деньги, внешний контракт). Не проходит — фича.

## Шаг 1а. Три вида строк — и почему вопросов мало

- **Решено** — код или документы уже дали ответ: образец, правило,
  проверка проставлены. Владелец подтверждает «актуально» или поправляет.
- **Верхний уровень** — из чего собрано и как разложено: тип архитектуры,
  границы модулей, фронт и его связь с бэком, хранение, права, виды
  проверок. Единственное, о чём спрашивают до задач: потом не переделать.
- **Всё остальное** — строка с `—` и правилом дословно **«решить при
  первой задаче, которая …»**: уведомления, состояния экрана, экспорт,
  транзакции, настройки, письма, любая мелочь. Вопросов нет. По этой
  фразе агент задачи узнаёт строку и решает её в предложении до кода.

Нашёл в коде одно и то же по-разному — расхождение: в верхнем уровне —
вопрос; мельче — строка «решить при первой задаче», с перечнем найденных
вариантов в правиле. Ответ владельца «потом» — та же строка, без спора.
Отложенную заботу нельзя вычеркнуть: строка и есть напоминание. Строк
должно хватать, чтобы каждый шаг сценария был кем-то задет (шаг 3).

## Шаг 2. Чек-лист уровней — к черновику, не к владельцу

По каждой оси пройди пять уровней: из чего собрано · как разложено · что
повторяется · как части договариваются · отделка. Пусто там, где продукт
потребует, — кандидат в таблицу с `—`. Для «Поверхности» уровни «как
договариваются» и «отделка» обязательны **как строки**, не как вопросы:
на первом прогоне они дают строки «решить при первой задаче».

## Шаг 3. Прогон сценариев

Два-три сценария, один — где что-то идёт не так. По шагам, называя
задетые заботы, впиши их в «Задевает». Шаг без заботы — дыра, кандидат в
таблицу. Забота без шага — подозрительна: сценария не хватает или это
фича.

## Шаг 4. Проверки — вторая таблица

Какие виды проверок дотягиваются до того, что трогают заботы; экран с
одними бэкенд-тестами не проверен. Виды проверок — верхний уровень, одна
пачка: у существующих статус «есть» с командой; недостающим владелец
ставит «отложено дата», «отклонено почему», «одобрено поставить» или
«решить при первой задаче».

## Шаг 5. Вопросы владельцу — только верхний уровень и подтверждение

Покажи таблицу целиком. Пачками по 4–6, варианты с ценой, рекомендуемый
первым «(рекомендую)»:
- подтверждение решённого: «нашёл так — актуально?»;
- верхний уровень: границы модулей, хранение, связь фронта и бэка,
  права, виды проверок — где код и документы молчат или спорят;
- решения дороже дня переделать — подтвердить, уйдут в ADR.

Дыра мельче верхнего уровня — не вопрос, а строка «решить при первой
задаче». Не спрашивай того, что есть в коде. После пачки: «что я не
спросил, но здесь важно?». Ответы — в файл сразу. Сказанное владельцем
записывается без фильтра. `[assumed дата]` — только там, где ошибка
дорога и владелец не ответил.

## Шаг 6. Записать

- `AGENTS.md`, «Каркас»: таблица `| Забота | Образец | Правило |
  Проверка |`, под ней правило из `../../sample/AGENTS.md` дословно;
  статуса нет; файл ≤ 200 строк — не влезает, режь объяснения, не заботы.
- `AGENTS.md`, «Тесты»: статусы. Другие разделы («Продукт», «Правила») —
  только по прямому решению владельца, минимально; ссылку на
  `docs/scenarios.md` в «Продукт» дописать, если нет.
- `docs/scenarios.md` — с заполненными «Задевает».
- `docs/rules/<область>.md` — когда у области три и больше правил или
  ловушек, нужных только при её правке; ≤ 30 строк; строка в «Что читать
  перед задачей»: «правишь `<маска>` — сначала `docs/rules/<область>.md`».
- `docs/decisions/NNN-*.md` — на решение дороже дня переделать; нумерация
  по журналу проекта, нет журнала — по форме образца.
- `docs/README.md` — новые файлы в карту.

## Шаг 7. Проверить себя

- `scripts/check-agents.sh` зелёный; в колонке «Правило» нет путей;
- нет строки без правила и без проверки одновременно, кроме честного
  `— / —` у ещё не решённого; отложенные строки — дословной фразой;
- ни одной строки из образца по содержанию; у сценариев заполнено
  «Задевает», есть сценарий с отказом; владелец видел таблицу до записи.

Отчёт: сколько забот, сколько решено, сколько «решить при первой задаче»;
что подтвердил владелец, что поправил; ADR; открытые вопросы.

## Повторный прогон

Запускается, когда фича упёрлась в строку «решить при первой задаче» или в
заботу без строки, и когда кода стало заметно больше. Начни со сравнения
по строке: новое / уточняет / противоречит / без изменений. Две разные
проверки: строка с образцом — существует ли путь и повторяет ли его второй
потребитель; образец в строке с `—` устареть не может — только `grep`, не
появился ли код без строки; правило в такой строке может — сверь с ADR.
Противоречие между сказанным и записанным — вопрос с вариантами, не
«последний сказавший прав». Появился код — впиши путь тем же PR.

## Чего не делать

- Не строить: ни кода, ни тестов, ни миграций.
- Не спрашивать о мелочах до задачи; не вычёркивать отложенное.
- Не вписывать образец, которого нет; не заводить колонку статуса.
- Не идти по сетке «оси × уровни» вопросами.
- Не заканчивать ход списком вопросов в тексте или обещанием.
