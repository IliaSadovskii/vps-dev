# docs-tidy

Документация растёт, потому что в неё пишут всё подряд: правило рядом с
объяснением, решение внутри разбора, снимок состояния рядом с ловушкой.
Дрейфует из этого ровно один класс — описание текущего состояния. Твоя
работа: найти, что какого класса, разложить по местам и срезать
`AGENTS.md` до того, что нужно в каждой сессии. Кода не трогаешь.

Прочитай перед началом, целиком:
- `../PRINCIPLES.md` §2, §3, §4, §8, §9 — что пишется, четыре класса,
  фильтр строки, самый опасный файл, что переезжает в ADR;
- `../asking.md`;
- в `../../sample/` — **только форма**: `AGENTS.md`, `docs/README.md`,
  `docs/decisions/`, `docs/<тема>.md`. Содержимое образца не переносится.

## Шаг 0. Инвентаризация — без правок

Собери таблицу всего, что есть: `AGENTS.md`, `CLAUDE.md`, `README.md`,
`docs/**`, файлы правил клиентов (`.cursor/rules`, `.claude/rules`,
`.github/copilot-instructions.md` и подобные), комментарии-эссе в коде
длиннее пяти строк. По каждому файлу: строк, когда последний раз менялся
(`git log -1 --format=%cs -- файл`), кто на него ссылается (`grep -rl`).

`docs/`, которые не попадают в контекст, **сокращать не надо**: цена у них
нулевая, пока они не врут. Сокращается только то, что читается каждую
сессию.

## Шаг 1. Разметить каждый кусок по классу

Пройди `AGENTS.md` и тематические документы разделами и абзацами, каждому
куску — класс:

| Класс | Признак | Куда |
|---|---|---|
| правило | требует, не описывает; есть или возможна проверка | `AGENTS.md`, одна строка, с колонкой «проверка» |
| решение | «выбрали X, а не Y, потому что»; дорого переделать | `docs/decisions/NNN-*.md`, 5–15 строк, датировано |
| ловушка | факт вне кода, на котором ошибались | `AGENTS.md`, строка с пометкой «(ловушка)» |
| замысел | как устроена подсистема и почему; связь правил и решений | `docs/<тема>.md`, ссылка из оглавления с условием чтения |
| описание состояния | «сейчас есть», «пока один модуль», «не установлено», списки файлов, версии | **удалить** или заменить командой, тестом, `git log` |
| знает сама | «используйте PSR-12», обзор фреймворка | удалить |

Разбор вариантов не устаревает, если датирован и помечен «принято»; тот же
разбор без даты посреди документа через полгода читается как описание
состояния. Такие куски — в ADR с ссылкой обратно на разбор, разбор остаётся
где был.

Дешёвые утверждения проверь: «`vendor/` не установлен», «тестов на X нет»,
«модуль один» — одной командой. Неверно — удалить; верно — всё равно
удалить, если ответ даёт команда за десять секунд.

## Шаг 2. Черновик раскладки — показать целиком

Составь план переезда до того, как что-то двигать:

- `AGENTS.md`: по разделам образца — что остаётся (строка → класс →
  проверка), что уезжает и куда, что удаляется и почему; ожидаемый размер;
- ADR: список кандидатов — заголовок, дата (из `git log` куска), откуда
  вырезан; нумерация по правилам `docs/decisions/README.md` проекта, нет
  журнала — по форме образца;
- `docs/<тема>.md`: что дописать из вырезанного, что оставить как есть;
- удаляемое — отдельным списком с причиной, по строке.

Правило владения (§4): правило — одна строка в `AGENTS.md`; почему — ADR;
где образец — строка каркаса; как работает — код и тест. Дубли между
слоями снимаются в пользу хозяина.

## Шаг 3. Вопросы владельцу — о спорном, не обо всём

Пачками по 4–6, варианты с ценой, рекомендуемый первым «(рекомендую)».
Спрашивай, когда:
- кусок читается и как правило, и как описание состояния;
- правило без проверки: оставить с «ревью», предложить проверку, убрать;
- решение без даты и без следа в `git log` — чьё оно и когда;
- удаление куска, на который ссылаются другие файлы.

Не спрашивай про то, что выводится из кода, и про куски, которым в любом
ответе одно место. После пачки: «что я не спросил, но здесь важно?».
Сказанное владельцем — записывается без спора.

## Шаг 4. Переезд

- Заведи ADR по форме образца; в старом месте — одна строка со ссылкой.
- Дополни `docs/<тема>.md` вырезанным замыслом; правил и решений там нет,
  только ссылки.
- Перепиши `AGENTS.md` по форме образца и бюджету `../../PLAN.md` §4:
  ≤ 200 строк, абзацев длиннее трёх строк нет, номеров строк нет, у правила
  колонка «проверка», у ловушки пометка. Раздел «Каркас», если его не
  было, — заголовок и три строки правила из образца; таблицу заводит
  `skeleton-talk`.
- `docs/README.md` — карта по форме образца, первая строка про правду и код;
  каждый файл `docs/` в карте, с условием чтения.
- `CLAUDE.md` — одна строка `@AGENTS.md`; файлы правил других клиентов —
  спросить: свести в `AGENTS.md` или удалить.
- `scripts/check-agents.sh`, если нет, — копия из образца, в `make lint` и CI.
- Ссылки на переехавшее — поправить (`grep -rn` по старым заголовкам).

Один коммит на ход: «вырезано в ADR», «AGENTS.md срезан», «карта docs/».
Ничего не удаляется насовсем без строки в списке шага 2, который владелец
видел.

## Шаг 5. Проверить себя

- `wc -l AGENTS.md` ≤ 200; сторож зелёный или красный только по каркасу;
- каждый ADR датирован, имеет статус и ссылку туда, где решение видно;
- ни одного куска класса «описание состояния» в `AGENTS.md`;
- ни одной битой ссылки внутри `docs/` (`grep` по путям в бэктиках);
- удалённое перечислено в отчёте с причиной.

Заверши отчётом: было → стало по строкам для `AGENTS.md`; сколько ADR
заведено; что переехало в `docs/<тема>.md`; что удалено и почему; открытые
вопросы.

## Чего не делать

- Не сокращать `docs/`, которые не читаются каждую сессию.
- Не переписывать смысл: переезд, не редактура.
- Не удалять молча — только по списку, показанному владельцу.
- Не трогать код и тесты; комментарий-эссе в коде — предложить ADR, не
  править файл.
- Не переносить содержимое образца.
