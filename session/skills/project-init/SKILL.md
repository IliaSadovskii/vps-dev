# project-init

Ты заводишь файлы, которые агент читает при старте каждой сессии. Самый
опасный из них — `AGENTS.md`: он едет в контекст всегда, и лишняя строка в нём
стоит дороже пропущенной. Поэтому это не «сгенерируй файл», а «пройди
кандидатов и по каждому реши».

Прочитай перед началом, целиком:
- `../PRINCIPLES.md` §2, §4, §6, §7, §8 — что пишется, фильтр строки,
  как спрашивать, порядок для существующего проекта, три источника строк;
- `../asking.md` — правила опроса;
- `../../sample/AGENTS.md` и `../../sample/docs/README.md` — **только форма**:
  разделы, порядок, колонки, длина. Содержимое образца («Переговорки») сюда
  не переносится ни строкой.

Кода не пишешь. Раздел «Каркас» не заполняешь.

## Шаг 0. Что уже есть

Собери, не спрашивая: README, `Makefile`, манифесты и lock-файлы, CI,
раскладку каталогов, тесты по видам, линтеры и их конфиги, скрипты проверок,
существующие `AGENTS.md` / `CLAUDE.md` / `docs/`. Существующий `AGENTS.md`
не выбрасывай: каждая его строка — кандидат, проходит тот же фильтр.

Каждую команду, которую собираешься записать, **запусти**. Не запустилась —
не записывай, скажи владельцу.

## Шаг 1. Продукт — один открытый вопрос

Единственное место, где нужен рассказ, а не выбор. Спроси один раз:
что за продукт, кому, что значит «готово», что продуктом не является.
Если есть README или документы с ответом — покажи, что понял, и спроси только
о расхождениях. Запиши 6–10 строк. Сценарии не пиши — это `skeleton-talk`.

## Шаг 2. Черновик всего остального — из кода

Собери черновик разделов 1, 2, 5–12 (нумерация как в образце) **до вопросов**:

| Раздел | Откуда черновик |
|---|---|
| Проверить себя, поднять | все цели `Makefile` (`make help`), профили `docker-compose.yml`, шаги CI, README; только запущенные команды |
| Когда остановиться и спросить | список из `PRINCIPLES.md` §4 образца как основа |
| Стек и чего не брать | lock-файлы: имена пакетов, **без версий**; «не брать» — пусто, спросишь |
| Где что лежит | только каталоги, которых нет в умолчаниях фреймворка, и то, что из дерева не выводится |
| Правила | три источника: (а) существующие проверки — арх-тесты, тесты с правилом в названии, скрипты, шаги CI, конфиги линтера: каждая проверка → правило; (б) конвенции по коду — пометка «(по двум примерам)»; (в) сказанное владельцем — после вопросов |
| Ловушки | комментарии в коде, объясняющие обход или странность (`grep` по комментариям длиннее двух строк в `app/`, `config/`, `tests/`), — каждый такой комментарий кандидат; плюс спросишь: «на чём агент уже ошибался» |
| Стиль решений | повторяющиеся образцы в коде: где Data, где Actions, где значения |
| Тесты | виды по каталогам и `phpunit.xml`/аналогу; статус «есть» только тому, что запускается |
| Git | ветки из истории, форма коммитов из `git log`, форма описания PR — из образца |
| Что читать перед задачей | существующие `docs/*` с условием чтения, если условие видно |

## Шаг 3. Фильтр каждой строки-кандидата

По каждой строке черновика реши и отметь:

1. **Удалить — агент ошибётся?** Нет, или ответ даёт одна команда за десять
   секунд — вычеркнуть (списки файлов, версии, сигнатуры, что уже сделано,
   как работает).
2. **Модель знает сама?** «Используйте PSR-12», «пишите тесты» — вычеркнуть.
   Оставить только то, что знаешь ты об этом проекте.
3. **Правило без проверки** — пожелание. Три исхода: найти существующую
   проверку; предложить новую (тест, скрипт) — владельцу, не писать самому;
   оставить с проверкой «ревью», если владелец так решил.
4. **Ловушка** — факт вне кода, на котором ошибались; пометка «(ловушка)».
5. Абзац длиннее трёх строк — в `docs/`, здесь ссылка. Номера строк не
   пишутся: имя теста, функции, раздела.

## Шаг 4. Вопросы владельцу — только о дырах

Покажи черновик разделами, вычеркнутое — отдельным списком «убрал, потому
что». Спрашивай пачками по 4–6, варианты с ценой, рекомендуемый первым
с пометкой «(рекомендую)». Не спрашивай того, что есть в коде, и того, где
все ответы ведут к одной работе — реши и пометь «(допущение)».

Что обычно остаётся спросить:
- «чего не брать» — пакеты и подходы, к которым агент потянется;
- правила без проверки — какой из трёх исходов;
- ловушки — на чём уже ошибались; проект пустой — ловушек нет по
  определению, раздел не заводится, а требование владельца — правило;
- виды проверок, которых нет — статус: «отложено дата», «отклонено почему»,
  «одобрено поставить»; вида нет — это решение владельца, не твоё;
- когда останавливаться — что добавить к списку;
- размер PR, чего никогда не делать в git.

После ответов — «что я не спросил, но здесь важно?». Ответы пиши в файл сразу,
с пометкой «выбор владельца». «Не знаю» — открытый вопрос в `docs/README.md`.

Владелец сказал — записывается, даже если фильтр не пропускает.

## Шаг 5. Записать

- `AGENTS.md` по форме образца: порядок разделов, таблицы там, где три
  колонки. Раздел «Каркас» — заголовок и правило под таблицей из образца
  дословно, таблица появится от `skeleton-talk`. Бюджет: ≤ 200 строк всего,
  ориентиры по разделам — `../../PLAN.md` §4.
- `CLAUDE.md` — одна строка `@AGENTS.md`.
- `docs/README.md` — первая строка «правда — код и тесты; документы говорят,
  где искать и почему так решили», карта существующих документов, открытые
  вопросы.
- `scripts/check-agents.sh` — копия `../../sample/scripts/check-agents.sh`,
  подключить в `make lint` (или аналог) и в CI тем же способом, каким
  подключены остальные проверки проекта. Нет ни `Makefile`, ни CI (новый
  проект) — не подключать, записать открытым вопросом в `docs/README.md`:
  «подключить тем же PR, что заведёт сборку». До `skeleton-talk` сторож
  красный по таблице каркаса — так и скажи.

## Шаг 6. Проверить себя

- каждая команда в разделе 1 запускалась в этой сессии;
- `wc -l AGENTS.md` ≤ 200; абзацев длиннее трёх строк нет; номеров строк нет;
- у каждого правила есть колонка «проверка»; у каждой ловушки пометка;
- ни одной строки, скопированной из образца по содержанию;
- ни одной строки, которую модель знает без этого файла.

Заверши отчётом: что записал, что вычеркнул и почему, что помечено
«(допущение)», открытые вопросы, и одной строкой — «следующий шаг:
`skeleton-talk`».

## Чего не делать

- Не спрашивать открытыми вопросами ни о чём, кроме продукта.
- Не ссылаться на образец как на довод («как в образце»): образец —
  форма, стек и решения там чужие. Довод — код проекта или ответ владельца.
- Не заводить раздел под то, чего ещё нет («появится позже»): раздел
  появляется вместе с фактом.
- Не заполнять раздел «Каркас» и не писать сценарии.
- Не переносить содержимое образца: он про другой продукт. Это касается и
  строк, которые выглядят общими — стоп-лист, правила git, «никогда»: они
  выводятся из истории проекта и ответов владельца, из образца только форма.
- Не писать код, тесты и проверки — только предлагать.
- Не заканчивать ход списком вопросов в тексте: вопросы задаются
  интерактивно и ждут ответа.
