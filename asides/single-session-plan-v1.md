# Разработка в одной сессии: план обвязки проекта

Дата: 2026-09-10. Составлен по разговору владельца с агентом.
Предшественники: `session-flow-brief.md` (что обсуждали), `session-flow-review.md`
(разбор от другой модели), `research/01..03` (фактура с источниками).

Этот файл — то, что предлагается делать, с обоснованием и с честной пометкой,
где обоснование — проверенный факт, а где суждение автора плана.

---

## 1. Чего хочет владелец и почему

Владелец — программист, работает один, ведёт несколько проектов. Год строил
оркестраторы: скиллы в Claude Code, затем свой оркестратор, затем цепочки ролей
поверх клиента Agent of Empires. Цепочки работают, но дают три проблемы:

1. **Долгий круг.** Цепочка идёт часами, поэтому подсознательно хочется
   надиктовать в неё побольше — «чтобы было на что посмотреть». Срез растёт.
2. **Огромный pull request на выходе.** Несколько шагов правят друг друга,
   код разрастается, проверить его глазами невозможно. Владелец перестаёт быть
   на воротах и начинает принимать на веру.
3. **Архитектура достаётся агенту.** В цепочку закладывается крупная фича,
   и агент принимает десятки решений сам.

Для проектов-полигонов это приемлемо. Для основного проекта — нет.

**Основной проект** — `listate-crm`, CRM для агентства недвижимости, пишется
за деньги, передаётся заказчику снимком без истории git. Это переписывание
проекта `wlist`, который владелец вёл годами и который вышел плохим
архитектурно (копипаста во фронте, отсутствие каркаса, ручные обходы). Цель
переписывания — чистая архитектура, расширяемость, отсутствие дублирования.

**Новый формат работы, который владелец хочет попробовать:** одна сессия,
мелкие срезы. Надиктовал маленькое — агент сделал — владелец прочитал дифф —
слил PR — дальше. Не цепочка, а разговор, но с обвязкой, которая держит
качество.

**Что должно дать обвязку смысл.** Голый разговор в чате уже существует и
работает плохо в одном месте: агент не знает, что в проекте уже решено, и
строит фичу без каркаса. Живой пример, из-за которого всё затевалось:

> Задача T26, права пользователя. Бэкенд спроектировали хорошо. Для проверки
> нужен был интерфейс — владелец сказал «сделай фронт из того, что есть».
> Агент собрал работающий макет страницы: без лайаута, без разделения
> компонентов, без решения о том, где лежат стили, как работает адаптивность,
> где живут уведомления, загрузка и промежуточные данные. Работает — и
> подлежит переписыванию целиком.

Правильный порядок был бы обратный: сначала каркас фронта (лайауты, компонентный
подход, сквозные части), потом страница на нём. Автоматически это не произошло
и не произойдёт: агент не знает, что каркаса нет, и не считает своим делом
это заметить.

**Отсюда три требования к обвязке:**

- агент понимает, что за приложение, какой стек, какие правила — без повторения
  голосом каждую сессию;
- агент **до** кода сверяется с каркасом и, найдя непостроенный слой, предлагает
  построить его отдельным PR, а не выдумывает заглушку;
- документация не отстаёт от кода, и за этим следит механика, а не дисциплина.

**Дополнительное требование:** формат должен быть одинаков во всех проектах
владельца — и в новых, и в уже начатых, где `docs/` заполнялась свободно.
Заводить его руками в каждом проекте владелец не хочет: нужен набор скиллов,
который разворачивает и заполняет структуру, опрашивая владельца.

**Оркестратор не выбрасывается.** Он остаётся вторым режимом — для задач, где
владелец готов доверить архитектурные решения агенту и не читать дифф лично.

## 3. Раскладка документов

Правило отбора: файл заводится, только если отличается от соседей **условием
чтения** или **сроком жизни**. Иначе это раздел файла, а не файл.

```
AGENTS.md              правила + оглавление      старт сессии          ≤150 строк
CLAUDE.md              @AGENTS.md                —                     1 строка
docs/product.md        что за продукт + сценарии старт сессии          ~50 строк
docs/concepts.md       каркас: заботы, проверки  старт сессии          ≤50 строк
docs/rules/*.md        правила по маске пути     при касании файла     ≤30 строк каждое
docs/decisions/        ADR, append-only          по требованию         растёт
docs/<тема>.md         замысел подсистемы        по требованию         как есть
docs/README.md         карта: чему верить        по требованию         ~15 строк
scripts/check-*.sh     сторожа                   —                     —
.oneway                маски необратимого        —                     —
```

**`CLAUDE.md` — не симлинк, а файл со строкой `@AGENTS.md`.** Причина: Claude
Code отказывается писать через симлинк («Refusing to write through symlink»,
намеренная защита), а файл правил агент должен уметь править сам.

### 3.1. Почему именно эти

- **`AGENTS.md`** — единственное, что гарантированно в контексте. Значит туда
  только то, что нужно в каждой задаче.
- **`product.md`** отдельно, потому что меняется раз в квартал, а правила —
  каждую неделю.
- **`concepts.md`** отдельно, потому что нужен в момент начала задачи и имеет
  свой сторож размера.
- **`decisions/`** отдельно, потому что append-only. Файл, который только
  дописывается, физически не может дрейфовать; смешивать его с правимым —
  терять это свойство.
- **`docs/rules/`** отдельно, потому что грузится условно.

### 3.2. Четыре класса знания по сроку жизни

Дрейфует ровно один:

- **правило** — оно *требует*, а не описывает. Код разошёлся — это баг кода,
  ловится тестом. Не устаревает;
- **решение (ADR)** — датировано, не правится, перекрывается новым.
  Не устаревает;
- **каркас** — забота → статус → путь-образец. Путь проверяет сторож;
- **описание текущего состояния** — единственный дрейфующий класс.
  Стратегия: сжимать до нуля, заменять тестом, схемой, `git log`.

Класс `docs/notes/` (снимки с датой) в первой редакции плана был, затем
исключён: это единственный дрейфующий класс, а всё его содержимое имеет место
получше (план среза → описание PR; разбор, к чему-то приведший → ADR; разбор,
ни к чему не приведший → выбросить). Заводится по симптому: срез не влезает
в один PR и следующей сессии нужен план от предыдущей.

### 3.3. Сценарии

8–10 сквозных проходов на настоящих именах и числах, разделом в `product.md`.
Нужны не сами по себе, а как **инструмент проверки полноты каркаса** (см. §6.4)
и описания продукта: там, где честный ответ на шаге — «ну, добавим ещё поле»,
описание неверно, и это видно сразу.

Спорное: при росте до тридцати сценариев `product.md` перестанет быть коротким
и его придётся выселять в отдельный файл.

### 3.4. Что пишется, а что выводится из кода

Тест: **можно ли получить ответ одной командой за десять секунд?** Если да —
не пишем, пишем команду.

**Не писать:** список файлов и каталогов, версии и зависимости, сигнатуры,
структуру таблиц, список маршрутов, что покрыто тестами, что уже сделано,
как оно работает.

**Писать:** *почему* (отвергнутых вариантов в коде нет по определению);
*запреты* (отсутствие пакета в зависимостях читается как «ещё не поставили»,
а не как «не бери»); *невидимые связи* (следствие двух вещей в разных файлах);
*намерение* — код показывает, как есть, и никогда не говорит, задумано ли это.

Проверочный вопрос на каждую строку-кандидат: если её удалить, агент
**ошибётся** — или просто потратит десять секунд на команду? Второе — удаляем.

**Переход «намерение → ссылка на код».** В чистом проекте кода нет, запись
законна как намерение. Когда код появился, запись не удаляется, а сжимается
до пути-образца. В `concepts.md` это заложено формой таблицы:

```
| Границы модулей | нужна, не построена | — | домен не знает про HTTP | — |
                              ↓ появился код
| Границы модулей | построена | app/Domain/Auth/ | домен не знает про HTTP | tests/Arch/ArchitectureTest.php:21 |
```

Кто следит за переходом — см. §7.3.

## 4. Механика подмешивания

### 4.1. Пять механизмов, не два

| # | Механизм | Когда | Кто решает | Надёжность |
|---|---|---|---|---|
| 1 | файл правил (`AGENTS.md`) | старт сессии | никто, безусловно | детерминированно |
| 2 | правило по маске пути | агент трогает файл по маске | клиент | детерминированно |
| 3 | хук на событие | точка цикла | твой скрипт | детерминированно |
| 4 | скилл | описание подошло к задаче | модель | на усмотрение |
| 5 | чтение файла по ссылке | модель решила | модель | на усмотрение |

### 4.2. Что и когда

| Момент | Что подмешивается | Механизм | Раз за сессию |
|---|---|---|---|
| старт сессии | `AGENTS.md` + `@product.md` + `concepts.md` | 1 | 1 |
| агент открыл файл по маске | `docs/rules/<тема>.md` | 2 или 3 | по факту |
| перед первой правкой кода | строка «выпиши задетые заботы и виды проверок; есть „не построена“ — стоп» | 3, `PreToolUse` | 1 |
| перед правкой необратимого | отказ + «спроси владельца» | 3, `PreToolUse` | по факту |
| конец хода | «тронул `app/**`, тестов нет — не заканчивай» | 3, `Stop` exit 2 | по факту |
| после компакции | `AGENTS.md` заново с диска | сам клиент | — |

**Стартовый бюджет:** ~150 + ~50 + ~50 = 250 строк ≈ 3200 токенов ≈ 1.6% окна.

**Отвергнутый вариант:** подмешивать `concepts.md` в каждый промпт. Цена —
30 копий по 1300 токенов за сессию (~39k), плюс половина сообщений владельца
(«нет, не так», «покажи диффом») не имеет отношения к каркасу, а нерелевантный
контекст не нейтрален. Владелец предложил ограничиться стартом сессии,
принято. Обсуждался промежуточный вариант — повтор раз в 15 промптов; не взят.

**Единица счёта — правила, а не байты.** По IFScale деградация идёт от числа
инструкций. 40–60 правил в `AGENTS.md` комфортно, 200 — начнёт терять,
независимо от числа строк.

### 4.3. Автопамять клиентов

Проверено: в `~/.claude/projects/-home-dev-projects-listate-crm/memory/` пусто —
за всё время работы над проектом автопамять не записала ничего. Значит проблема
двух источников правил пока гипотетическая. Решение: ничего не выключать,
завести правило «появились файлы в каталоге памяти — прочитать и решить: либо
перенести в `AGENTS.md` под сторож, либо удалить».

Отвергнуто: глобальное выключение. Владелец работает и вне проектов с обвязкой,
там автопамять полезна. Настройка `autoMemoryEnabled` проектная, но в скелет
пока не кладётся.

## 5. Содержимое `AGENTS.md`

### 5.1. Разделы в порядке частоты промахов

Порядок неслучаен: первые строки файла модель держит лучше (primacy).

1. как себя проверить — одна команда, где логи, чем посмотреть глазами;
2. как поднять проект одной командой;
3. **когда остановиться и спросить** — схема БД, публичный контракт, новая
   зависимость, необратимая миграция;
4. где что лежит — таблицей, с путём-образцом, не описанием;
5. стек и **чего не брать** (список запретов работает лучше списка разрешений);
6. стиль решений — таблица «случай → чем»;
7. линт и формат — одна команда с авто-фиксом;
8. git: ветки, размер PR, форма описания;
9. что не трогать никогда;
10. оглавление: по строке на файл, **с условием чтения**.

### 5.2. Фильтр, который держит размер

**Правило, под которым нет сторожа или ADR, в `AGENTS.md` не пишется.**
Нечем проверить — значит это пожелание; агент нарушит его без последствий,
а строку придётся возить в контексте вечно.

Плюс запрет, ловящий копипасту из `docs/`: **абзацев длиннее трёх строк нет**.
Длинный абзац — это документация, ей место в `docs/`.

### 5.3. Правила владения (против дублирования между слоями)

| Что | Хозяин | Как у остальных |
|---|---|---|
| правило | `AGENTS.md`, одна строка | — |
| почему так решили | ADR | ссылка `docs/decisions/NNN-*.md` |
| где образец в коде | `concepts.md`, путь | — |
| как оно работает | код и тест | не пишем |

Автоматически дубли прозы не ловятся — инструментов нет (`jscpd` только для
кода). Держится на правиле владения, сторожах размера и на том, что файлы
маленькие.

### 5.4. Строки-правила, перенесённые из цепочки ролей

Отобраны прочёсыванием `orch/prompts/` (4509 строк). Каждая проверена
на переносимость в одну сессию.

**Прежде чем решать (из `role-solution.md`), ~8 строк:**

```
Выбираешь пакет, подход или версию — ищи, не вспоминай.
Правишь существующее по образцу — не ищи.

- Начинай с официального, но документации той версии, что стоит в проекте
  (`composer.json`, `package.json` — путь и строка).
- Официальным не заканчивай: issues, обсуждения, разборы практиков.
  Документация говорит, как задумано; о том, как оно себя ведёт, пишут
  в другом месте.
- Метка на каждое утверждение: [проект] путь:строка · [источник] ссылка ·
  [допущение].
- Один голос — мнение. Повторяющийся у независимых людей образец — практика.
- Совет трёхлетней давности о переписавшейся библиотеке — ловушка.
- Не нашлось — законный итог. Скажи «не нашёл», не заполняй из памяти.
```

Порог в первой строке обязателен, иначе правка кнопки станет ресёрчем.

**Мнимая развилка (оттуда же), 3 строки:**

```
Проект уже решил — это не развилка. Найди, где решено, и следуй
(путь:строка). Один файл, делающий что-то одним способом, — совпадение,
не конвенция. Конвенция — повторяющийся образец или записанное правило.
```

Вторая половина — прямое лекарство от случая T26: агент собрал фронт «из того,
что было», приняв случайный образец за стандарт.

**Форма дороже поведения (оттуда же), 2 строки:**

```
Где лежат файлы, как называются, где граница модуля — по одному файлу
вкусовщина, на сотне определяет, можно ли в проекте что-то найти.
```

**Свидетельство, а не пересказ (из `role-implementation.md` §3), 2 строки:**
вывод команды вставляется дословно. Ловит «я проверил, всё работает».

**Тест красный по правильной причине (оттуда же §1), 2 строки:** тест первым
коммитом, до кода; красный именно из-за отсутствующего поведения, а не из-за
опечатки. Скрипт с трейлерами `Orch-Step` из `common-test-ownership.md`
в одну сессию не переносится — он про многошаговую цепочку.

**Все состояния экрана (из `skill-frontend.md`)** — в `docs/rules/frontend.md`,
грузится только при касании фронта: пустое, загрузка, ошибка, много данных,
нет прав.

## 6. Каркас

### 6.1. Определение через тест, а не через слова

```
Каркас — решение, которое следующая фича будет вынуждена повторить.
Сделал один раз и больше ни на что не влияет — не каркас, это фича.
```

Два фильтра: **повторится** (встретится хотя бы в каждой второй фиче) и
**переделка дороже записи** (менять придётся в двадцати местах).

Критерий не зависит от вкуса и даёт разные ответы для разных проектов — это
правильно: в приложении из трёх экранов «как общаются компоненты» действительно
не каркас.

### 6.2. Шесть осей — по потоку, а не по стеку

«Фронт и бэк» ломается на CLI, библиотеке, конвейере данных. Универсально то,
что идёт по потоку работы:

| Ось | Что спрашиваем | В CRM | В CLI |
|---|---|---|---|
| Поверхность | через что приходит работа | экраны, формы, навигация | команды, флаги, ввод |
| Хранение | что живёт дольше запроса | таблицы, файлы, кэш | конфигурация, состояние |
| Обработка | где логика и её границы | домены, действия | модули |
| Выход | что уходит наружу | ответы, ошибки, уведомления, выгрузки | stdout, коды возврата |
| Сквозное | что задевает всё | права, транзакции, i18n, тема, конфигурация | те же |
| Проверка | чем это проверяется | виды тестов | те же |

По каждой оси в промпте лежит **затравка** из 5–8 типовых забот плюс жёсткое
требование: затравка — пол, не потолок; прочитай `product.md` и назови заботы,
которых в затравке нет, но которые в этом приложении повторятся (карта —
координаты; деньги — округление и валюты; импорт — идемпотентность).

### 6.3. Пять уровней глубины

Одинаковы для любой оси; агент идёт сверху и перед каждым следующим спрашивает,
называя, зачем он нужен и когда обычно не нужен:

1. **из чего собрано** — инструменты, пакеты, версии;
2. **как разложено** — каталоги, имена, где что лежит;
3. **что повторяется** — сквозные части этой оси;
4. **как части договариваются** — обмен, состояние, зависимости;
5. **отделка** — то, что видно человеку.

Уровни 1–3 применимы почти всегда, 4–5 — по симптому.

Это отвечает на реальную трудность владельца: он сам не знает заранее, какую
глубину считает каркасом, и не должен знать — глубина набирается по ходу,
с правом остановиться.

### 6.4. Проверка полноты — прогон сценариев

```
Возьми два-три сценария из product.md и пройди каждый шаг вслух, называя,
какие заботы он задевает. Забота, не названная ни одним сценарием, —
подозрительна. Шаг сценария, не покрытый ни одной заботой, — дыра в списке.
```

Проверено на случае T26: сценарий «администратор открывает список ролей и
снимает право» задевает навигацию, таблицу, пустое состояние, состояние
загрузки, права на элементах, подтверждение действия, уведомление об успехе —
семь забот, ни одной из которых в `listate-crm` нет. Список без этой проверки
их не находит, с ней — за две минуты.

### 6.5. Тесты как вторая таблица каркаса

Вопрос не «хватает ли тестов», а **какие виды проверок дотягиваются до того,
что задача трогает**. Из `role-plan.md`: «эндпоинт, проверенный с бэкенда,
ничего не говорит об экране»; «вида нет — решение владельца: установка
инструмента меняет зависимости и привычки проекта».

```markdown
## Проверки

| Вид | Есть | Команда | Что покрывает |
|---|---|---|---|
| модульные | да | make test | логика домена |
| интеграционные через БД | да | make test | миграции, запросы |
| браузерные | да | Pest Browser, tests/Browser/ | видимая сторона |
| визуальные (раскладка) | нет | — | — |
| контрактные для внешнего API | нет | — | — |
| проверки данных при миграции | нет | — | — |
```

Новых механизмов не требует: та же строка-требование перед первой правкой
кода спрашивает и про заботы, и про виды проверок.

### 6.6. Правило, делающее устаревание таблицы дешёвым

```
concepts.md — подсказка, а не правда. Правда — код.
Забота помечена «не построена» — сначала поищи в коде, потом строй.
Нашёл — построй строку, а не вторую реализацию.
```

Без него устаревшая таблица опасна (второй лайаут рядом с первым), с ним цена
промаха — двадцать секунд поиска. Общая формулировка идёт первой строкой
`docs/README.md`: **правда — код и тесты; документы говорят, где искать и
почему так решили.**

## 7. Сторожа и хуки

### 7.1. Скрипты

| Скрипт | Что проверяет |
|---|---|
| `check-agents-size.sh` | `AGENTS.md` ≤ 150 строк |
| `check-doc-paths.sh` | каждый путь в бэктиках существует; `путь:N` не дальше конца файла; `vendor/` запрещён |
| `check-pr-shape.sh` | дифф трогает `app/**` ⇒ трогает `tests/**`; трогает секции зависимостей ⇒ трогает `docs/decisions/`; в описании PR есть «Заботы: …» кроме «нет» ⇒ `docs/concepts.md` в диффе |
| `guard-oneway.sh` | путь совпал с маской из `.oneway` — отказ с текстом «спроси владельца; после ответа — `@одобрено <дата> <что>` в описании PR» |
| `rule-for-path.sh` | вернуть тело правила из `docs/rules/`, чьей маске соответствует путь |

Каждый скрипт объясняет в шапке, зачем он и **чего не ловит**.

### 7.2. Куда вешаются

- `guard-oneway.sh` и `rule-for-path.sh` — `PreToolUse`;
- строка-требование перед первой правкой — `PreToolUse`, флажок в `/tmp`,
  один раз за сессию;
- `check-pr-shape.sh` — `Stop` (exit 2, агент не может закончить ход) и CI
  как второй рубеж;
- `check-agents-size.sh`, `check-doc-paths.sh` — `make lint` и CI.

`Stop` сильнее CI: ловится в сессии, до PR, чинит сам агент.

### 7.3. Кто следит за переходом «не построена» → «построена»

Полностью автоматом не ловится: машина не знает, какие файлы относятся к какой
заботе. Три частичных механизма плюс свойство из §6.6:

1. **симметрия начала и конца** — назвал заботу в начале среза, отчитайся
   в конце; проверяется формой PR (`check-pr-shape.sh`);
2. **эвристика на новый каталог** — в диффе появился новый каталог верхнего
   уровня (`resources/js/composables/`, `app/Domain/Billing/`) → вопрос агенту,
   не блокирующий;
3. **владелец на воротах** — читает дифф, видит новую папку без строки.

### 7.4. Мультипровайдерность

Владелец работает в Claude через Agent of Empires, но имеет подписку Codex и
доступ к китайским моделям через OpenCode, и хочет сравнить все три на этой же
схеме.

Решение: **делать всё хуками, а не родными масками Claude.** У Codex и OpenCode
масок нет; если у Claude использовать родной механизм, а остальным эмулировать,
сравнение трёх клиентов будет нечестным — разные механизмы, разное поведение.
Одно тело правил в `docs/rules/`, один `scripts/rule-for-path.sh`, три тонких
адаптера.

**Непроверенное, выяснится при внедрении:** извлечение пути из `apply_patch`
в хуке Codex (по описанию делается); глобальный каталог скиллов OpenCode.

## 8. Скиллы

Тело — `SKILL.md` по открытому стандарту (agentskills.io), каждый ≤150 строк.
Каталоги: `.claude/skills` читает только Claude; `.agents/skills` читают Codex,
Gemini, OpenCode. Общего каталога для всех четырёх нет — держать `.agents/skills`
и симлинк из `.claude/skills`.

| Скилл | Когда | Что делает |
|---|---|---|
| `project-init` | новый проект, один раз | продукт → стек → `AGENTS.md` → сторожа → скелет `docs/`. Каркаса не касается |
| `skeleton-talk` | после init и **повторно**, когда упёрся | шесть осей, пять уровней, прогон сценариев. Пишет `concepts.md` + ADR. **Ничего не строит** |
| `docs-tidy` | проект, где уже что-то есть | инвентаризация `docs/`, раскладка по слотам, проверка дешёвых утверждений, вытаскивание «Решено» в ADR |

### 8.1. Общие правила опроса (отдельным файлом, как `common-*` в цепочке)

- пачками по 4–6 вопросов, рекомендуемый вариант первым;
- **показывать варианты, а не спрашивать открытым вопросом** — владелец
  не обязан иметь готовое мнение, но выбрать из трёх раскладок с ценой может;
- вариант всегда с ценой, не только с названием;
- ответ владельца пишется **в файл сразу**, а не остаётся репликой в чате;
- **проверять то, что записал**: каждая команда, попавшая в `AGENTS.md`,
  должна реально запуститься при генерации;
- «не знаю» — законный ответ, записывается как открытый вопрос;
- пакеты и подходы ищутся в сети по правилам из §5.4;
- после каждой оси обязательный вопрос: «что я не спросил, но здесь важно?»;
- **добавленное владельцем не проходит фильтр повторяемости** — сказал,
  значит записываем, спорить нельзя.

### 8.2. Адаптация существующего проекта — порядок обратный

Для проекта с кодом опрашивать с нуля глупо: половина решений уже принята,
просто не записана.

1. **вывести каркас из кода** — пройти по заботам и найти, что де-факто
   построено (есть `resources/js/layouts/` → лайауты построены, вот образец);
2. **показать владельцу таблицу** с проставленными статусами;
3. **спрашивать только про расхождения и дыры** — «уведомления нашлись в трёх
   местах по-разному, какой считать образцом?», «состояний загрузки не нашёл
   вообще, заводим?».

Дешевле опроса и точнее: код не врёт о том, что в нём есть.

### 8.3. `AGENTS.md` — самый опасный скилл

Единственный файл, который агент генерирует и который едет в контекст каждой
сессии. По нему есть **отрицательные данные**: ETH — сгенерированные моделью
контекст-файлы снижают долю успеха; Red Hat — «auto-generated context files can
hurt when full of generic information the model already knows».

Значит скилл не «сгенерируй файл», а «пройди кандидатов и по каждому реши»:

- на каждое правило-кандидат найти существующий сторож, предложить написать
  новый или **выбросить правило**;
- отличить «модель знает сама» («используйте PSR-12») от «знаешь только ты»
  («`lang/**/*.php` уезжает в публичный бандл целиком»);
- три источника правил, генерация — худший: опрос владельца, разбор промахов
  агента (второй раз ошибся — строка), извлечение из кода.

Стоит посмотреть, что режет `/doctor` в Claude Code (он предлагает вырезать
выводимое из кода), и повторить логику.

## 9. Что решено не брать

| Что | Почему |
|---|---|
| **OpenSpec** | Не про слои, а про один слой («что делаем в этом изменении»). Валидатор структурный, сверки кода со спекой нет. Окупается на крупных изменениях — прямое противоречие с мелкими срезами. Условие вернуться: срез не влезает в один PR и задевает больше двух модулей |
| **Memory Bank как инструмент** | Раскладку берём, инструмент нет: держится на дисциплине агента, стоит токенов каждую сессию, а его самый ценный слой (`activeContext`, `progress`) у владельца уже есть даром — git log, описание PR, тесты |
| **Сервисы памяти** (Mem0, Zep, Letta, Cognee) | Решают другую задачу — факты о пользователе и разговорах, когда артефакта нет; меряются на диалоговых бенчмарках. Для кода лучший результат получен на иерархии markdown без БД (ByteRover). Плюс риск устаревания у них **выше**: протухшую строку в md видно в диффе, протухший факт в векторной базе не видит никто |
| **EARS** | Критерии приёмки свободным текстом с одним требованием: каждая строка проверяема и становится одним тестом |
| **Kiro целиком** | Единственный, кто выложил steering + specs + hooks одним продуктом. Против: привязка к клиенту AWS при желании независимости; в CLI режимы включения steering не работают — грузится всё; пять CVE за год |
| **`docs/notes/`** | См. §3.2 |

## 11. Спорные места

Автор плана обозначает свою позицию; решение за владельцем.

### 11.1. Строка-требование перед первой правкой кода

**За:** `concepts.md` со старта сессии к сороковому сообщению уехал далеко,
а строка приходит вплотную к действию. 15 токенов, один раз за сессию.
**Против:** ещё один хук, ещё одно место, где что-то ломается.
**Позиция автора:** оставить.

### 11.2. Сторожа как класс

**За:** всё, что держится на «агент вспомнит», ломается. `AGENTS.md` вырос
вдвое за трое суток, и никто не заметил.
**Против:** пять скриптов плюс адаптеры под три клиента — это код, который
надо поддерживать, и он молча ломается при обновлении клиентов. Плюс `Stop`
с exit 2 может зациклить агента при плохо написанном условии.
**Позиция автора:** брать, но начинать с двух самых дешёвых (размер и пути),
остальные — после первого прогона. Тело всех хуков в одном месте, адаптеры
по три строки, раз в месяц ручная проверка «попроси агента править миграцию,
увидь отказ».

### 11.3. Мультипровайдерность сразу

**За:** у владельца есть подписки Codex и доступ к моделям через OpenCode,
он хочет сравнить; сравнение имеет смысл только на одинаковой обвязке.
**Против:** удваивает работу шага 5; у двух из трёх клиентов нет масок, что
вынуждает делать всё хуками, то есть отказаться от более надёжного родного
механизма Claude.
**Позиция автора:** делать, единым хуковым механизмом. Автор ранее предлагал
отложить — владелец возразил, возражение принято.

### 11.4. Скиллы-опросники

**За:** без них формат придётся заводить руками в каждом проекте; это
исходное требование владельца.
**Против:** самая хрупкая часть. Промпт на 150 строк, ведущий разговор
произвольной глубины, провалится первым: либо задолбает вопросами, либо пройдёт
по верхам. Ни ETH, ни Red Hat, ни Kiro такого не публиковали — steering-файлы
Kiro генерируются без диалога.
**Позиция автора:** делать, но после шага 3, против готового образца.

### 11.5. Сценарии в `product.md` или отдельным файлом

**Позиция автора:** разделом в `product.md`; выселить, если разрастутся.

### 11.6. Порог заведения ADR

Решение, на которое ушло больше десяти минут разговора, записывается. Порог
произвольный, лучшего не нашлось.

### 11.7. Лимит `AGENTS.md`: 150 или 200

Anthropic пишет «под 200», Red Hat «меньше 150». Обе цифры опираются на одну
работу и обе — оценка. **Позиция автора:** 150, потому что при мелких срезах
часть работы `AGENTS.md` делают глаза владельца, читающего каждый PR.
