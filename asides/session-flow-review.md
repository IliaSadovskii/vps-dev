# Разработка в одной сессии: разбор брифа, образец listate-crm, план для vps-dev

Независимый разбор от 2026-09-10. Вход: `asides/session-flow-brief.md`, три
отчёта в `asides/research/`, репозиторий vps-dev, живой проект
`/projects/listate-crm`. Всё, что ниже помечено «не проверял» или «не
уверен», так и читать.

## 0. Главный вывод

Метод уже построен — в `listate-crm`. Там есть всё ядро из брифа: `AGENTS.md`
с правилами, каждое из которых ссылается на проверку; три sh-сторожа и
arch-тесты в CI; журнал решений с шаблоном и статусами; карта `docs/`. Нового
инструмента не нужно ни одного. Нужны три вещи:

1. **Урезать `AGENTS.md` с 613 до ~200 строк и поставить на размер сторож
   в CI.** Файл вырос с 295 до 613 строк за три дня (5–8 сентября, 26 правок),
   и рост сделали роли оркестратора коммитами «сказано там, где его читают» —
   это compound-петля без сборки мусора, ровно тот режим отказа, что описан
   у критиков Compound Engineering. Половина файла — документация проекта
   и снимок состояния, а не правила.
2. **Заменить механикой четыре места, где схема брифа держится на
   дисциплине:** размер контекст-файла, живость ссылок `путь:строка`, «тесты
   в том же PR», «стоп перед необратимым». Всё четыре — скрипт на 20–40
   строк или хук; ничего покупать не надо.
3. **В vps-dev завести не «метод», а раздатчик проверенного:** `project new
   --like listate-crm` копирует сторожа и скелет из живого проекта, роль
   `style` кладёт три короткие справки `work/` и глобальные скиллы.

Ни OpenSpec, ни Memory Bank, ни EARS, ни compound-плагин брать не надо.
Оркестратор остаётся вторым режимом; от него в первый режим переезжает одно —
`role-conventions.md` как тело опросника.

## 1. Фактура: что дочищено и что меняет решение

Только то, что влияет на план. Остальное — в `research/*.md`.

- **Claude Code не читает `AGENTS.md`; `CLAUDE.md` должен быть `@AGENTS.md`,
  не симлинк** (запись через симлинк отвергается, #66559). `listate-crm` уже
  так и сделан. Бриф в §5 п.1 говорит «симлинк» — исправить.
- **Gemini CLI читает `AGENTS.md` только по настройке** `context.fileName:
  ["AGENTS.md","GEMINI.md"]` в `settings.json`. Это настройка машины, не
  проекта → роль `style` (у неё уже есть механика точечной правки
  `~/.claude/settings.json`). Сейчас в `~/.gemini/settings.json` этого нет.
- **Пре-тул хуки с запретом есть у всех четырёх CLI** — это меняет ответ на
  требование «не додумывать в дорогих местах»: остановка может быть
  механической, а не просьбой в промпте.
  - Claude Code: `PreToolUse`, matcher `Edit|Write`, `permissionDecision:
    deny|ask` (`.claude/settings.json`).
  - Codex: `PreToolUse` в `.codex/hooks.json`, deny через
    `permissionDecision` или exit 2; перехватывает `apply_patch` (хук видит
    текст патча, путь надо вытащить из него — проверить при внедрении).
  - Gemini: `BeforeTool` в `.gemini/settings.json`, matcher
    `write_file|replace`, JSON `{"decision":"deny","reason":…}`.
  - OpenCode: плагин `tool.execute.before`, `throw` блокирует; инструменты
    `edit|write|apply_patch`.
  Четыре тонких адаптера, один общий скрипт.
- **ETH Zürich (arXiv 2602.11988), по абстракту:** контекст-файлы в среднем
  не поднимают успех и стоят +20 % на инференс; **инструкции агенты
  выполняют хорошо, обзоры репозитория («repository overviews») бесполезны**.
  Цифры −3 %/+4 % в абстракте не приведены — не цитировать. Для нас важна
  вторая половина: в 613 строках `AGENTS.md` обзорная часть — мёртвый вес,
  а правила со ссылкой на проверку — то, что работает.
- **Pest arch умеет `toOnlyUse` / `toOnlyBeUsedIn`** — для правил вида
  «страницы не ходят в БД» и «действия зовут только из дверей» готовые
  выражения. Свой тест «домены не лезут друг в друга мимо публичного
  контракта» они не заменяют (правило динамическое, по имени домена) —
  оставить как есть. Deptrac не нужен.
- **jscpd 5.x** (Rust-ядро, npm): PHP и Vue в списке, `--threshold` в
  процентах роняет CI. **dependency-cruiser** понимает `.vue` через
  транспилятор проекта. **eslint-plugin-boundaries** для `.vue` не
  подтверждён (README о Vue молчит); в `listate-crm` ESLint нет вовсе — на
  16 файлах фронта и не нужен.
- **OpenSpec `validate` проверяет формат дельт, не код против спеки**
  (#880 открыт с марта); дрейф — главная жалоба практиков; «2M токенов/день»
  не нашлось, «4 истории/16 критериев на багфикс» — про Kiro. Аргументы
  брифа «за» остаются, «против» подтверждены.
- **GSD заархивирован, Open GSD жив;** идея «свежая сессия на фазу, план
  файлом» подтверждена практиками и уже реализована в orch (`context:
  fresh`). Context rot задокументирован (NoLiMa: при 32k 11 из 13 моделей
  ниже 50 % от короткого контекста).
- **Cognition, апрель 2026:** «запись однопоточная, остальные агенты дают
  мнение, не действия»; clean-context ревьюер даёт ~2 бага на PR. Это
  подтверждает выбор владельца и оставляет одну дешёвую опцию: read-only
  ревьюер в свежей сессии перед чтением PR владельцем.
- **Пределы размера:** Anthropic docs — «до 200 строк на файл, длиннее —
  хуже следование»; Red Hat — «меньше 150; для маленьких репо 30–50».
  «~150 инструкций» — интерпретация IFScale, в статье порога нет.
- `role-conventions.md` в orch уже требует «до ~150 строк», «версия из
  манифеста, команда после запуска, строка после открытия файла», один
  пакет вопросов владельцу. Это и есть опросник из брифа §5, написанный и
  прогнанный. Без ворот в CI его собственный предел размера не держится —
  что и показал `listate-crm`.

## 2. `listate-crm` как образец

Факты: 169 коммитов, `AGENTS.md` 613 строк (+15 незакоммиченных),
`docs/` — 19 тематических файлов (3 200 строк) + 5 ADR, CI — 13 шагов
проверок, 4 sh-сторожа, 8 arch-правил + 3 своих теста, покрытие типами 100 %.

### 2.1. Что удачно и переносится в шаблон как есть

- **`CLAUDE.md` = `@AGENTS.md`.** Верно по документации, не симлинк.
- **Правило → проверка.** Почти каждое правило в «Как здесь пишут код»
  и «Правила, которые нельзя нарушать» заканчивается
  `tests/Arch/ArchitectureTest.php:NN` или `scripts/check-*.sh`. Это
  главный паттерн: правило не описывает состояние, а требует его, и у него
  есть сторож. Переносится как **форма строки** в скелете `AGENTS.md`.
- **Два слоя сторожей с объяснённой причиной.** `check-boundaries.sh`
  (текстовый grep) рядом с arch-тестом, потому что тест не видит классов,
  которых нет в `vendor/`. Причина записана в самом скрипте. Общий принцип
  для шаблона: sh-grep ставится там, где инструмент стека ещё не видит.
- **Arch-тесты падают на пустом множестве** (`not->toBeEmpty()`,
  `$checked > 0`). Редкая и правильная защита от пустой истины. В шаблон —
  как обязательное свойство любого своего сторожа.
- **`check-migrations.sh` с пометкой `@sujenie`.** Запрет с лазейкой,
  которая оставляет след в диффе и заставляет автора объяснить. Ровно эта
  форма нужна для «стоп перед необратимым»: хук останавливает, пометка в
  диффе показывает владельцу, что остановка была и чем закрыта.
- **`check-comments.sh` как маршрутизатор знания:** длинная проза в коде →
  «это решение, неси в `docs/decisions/`». Механика распределения по
  классам документации, а не пожелание.
- **Журнал решений:** шаблон, статусы `принято/заменено/отменено`, порог
  «дороже одного дня переделать», 5–15 строк, файл не правится.
  Переносится целиком (`docs/decisions/README.md`, `000-template.md`).
- **`docs/README.md`** с разделом «чего здесь нет» — карта, а не свалка.
- **«Когда работа считается сделанной»** — 7 строк, определение готовности.
- **Таблица «Что за данные → чем делаем → пример в коде»** и таблица
  «Работаешь над → прочитай сначала» — эталон по ссылке и прогрессивное
  раскрытие, то же устройство, что `style/machine/*.md` на машине.
- **ADR 005 «строгость с первого дня»** — правильный ответ для greenfield,
  и он же аргумент: сторож на размер `AGENTS.md` ставится сейчас, пока
  файл один.

  сказано» — вот статусы `построен/не построен`. Место им в
  `docs/concepts.md` с колонкой «пример в коде», а не в правилах.

### 2.3. Что в `docs/` не документация проекта, а разговор с самим собой

`docs/FRONTEND.md` (§1 «главная развилка», §2 «сколько стоит каждый
вариант», §6 «Решено»), `STACK.md` («реестр решений»), `MODULES.md` §8 «что
рассматривали и отвергли» — по содержанию это ADR, разложенные по темам.
Ничего страшного: `decisions/README.md` прямо разрешает длинный разбор
держать в тематическом документе, а в ADR класть вывод и ссылку. Но у пяти
ADR ссылки на эти разборы есть, у десятка решений внутри `FRONTEND.md` и
`STACK.md` — ADR нет. Команда «привести доку к формату» из брифа здесь
должна сделать одно: вытащить из тематических файлов «Решено» в короткие
ADR со ссылкой обратно. Переименовывать `docs/decisions/` в
`docs/arc42/09-decisions/` не надо — номера arc42 ничего не добавляют.

## 3. Суждение

### 3.1. Полезно для «соло, greenfield, мелкие срезы, читаю каждый PR»

- `AGENTS.md` ≤ 200 строк, каждое правило — со ссылкой на сторож или на ADR.
- Тесты как приёмка, тест первым коммитом в PR (в orch это уже
  `common-test-ownership`; в одной сессии — правило + сторож «код без теста
  не проходит», см. 3.4).
- Ворота в CI: то, что есть в `listate-crm`, плюс четыре новых сторожа
  (3.4). Копипаста — jscpd, сначала как отчёт, порог после первого прогона.
- ADR по порогу «дороже дня переделать» + `check-comments.sh` как
  маршрутизатор.
- Хуки на необратимое во всех четырёх CLI.
- Свежая сессия на срез — бесплатно в AoE, состояние в репозитории и PR.
- Read-only ревьюер в свежей сессии перед чтением PR владельцем — опция,
  дешёвая, по цифрам Cognition окупается. Не действия, только находки.

### 3.2. Мода и лишний вес

- **OpenSpec / Spec Kit / Kiro / BMAD / GSD** — для мелких срезов и одного
  читателя PR не нужны. Валидатор OpenSpec код не проверяет; спека, которая
  не исполняется, — вторая копия теста и источник дрейфа. См. вопрос 1.
- **Memory Bank.** `activeContext.md` и `progress.md` — это класс «снимок»,
  тот самый, что в `listate-crm` протух первым («Состояние», «vendor не
  установлен»). Заводить файлы, которые по определению живут от сессии до
  сессии и обновляются «по аккуратности агента», — заводить дрейф нарочно.
- **EARS, VSDD, формальная верификация** — не для 5–20-минутных срезов.
- **Context Store, llms.txt, C4, Tessl** — наблюдать, не внедрять. C4 —
  когда появится второй сервис.
- **Compound-плагин** (50 агентов, 38 команд) — сама петля нужна, плагин нет.
  Петля в одной сессии: замечание владельца на диффе → правка → если промах
  повторяемый, одна строка в `AGENTS.md` тем же PR; сторож размера заставит
  что-то выкинуть взамен. Это и есть сборка мусора.
- **arc42-номенклатура** — слоты верные, имена лишние.

### 3.3. Где бриф неправ или неточен

1. **«`CLAUDE.md` — симлинк»** — нет, `@AGENTS.md` (см. §1).
2. **«Каркас — таблица со статусами `построен / не построен`».** По
   собственной таксономии брифа это класс «снимок», он протухнет как
   `progress.md`. Держится только если статус *выводится*: колонка «пример в
   коде» с путём, и сторож проверяет, что путь существует. Забота без пути —
   «не построена» по факту, а не по записи. Так таблица становится
   проверяемой.
3. **«Рефлекс перед фичей — всегда, без вызова»** — это дисциплина в чистом
   виде, самая ненадёжная строка плана. Механика, которая ловит последствия:
   на каждую построенную заботу — **запрещающее правило** (arch-тест или
   dependency-cruiser: «страницы не импортируют `axios`/`fetch`, только
   `support/http`», «компоненты страниц не держат свой toast»), плюс jscpd на
   вторую реализацию. Сам список забот до кода — раздел в шаблоне описания
   PR; его читает владелец. Остаток честно дисциплинарный.
4. **«Разговор о каркасе, ищет пакеты в интернете»** — у `listate-crm` он
   уже проведён руками: `STACK.md` §20 «пакеты первого захода»,
   `FRONTEND.md`. Команда нужна для следующего проекта, а для этого — только
   вторая половина: фронтовые заботы (уведомления, состояния загрузки, права
   на элементах, глобальная валидация) в `concepts.md` как пустые строки.
   Живой пример провала из брифа («построй фронт для страницы прав») закроют
   именно эти четыре строки, а не команда.
5. **«Поставить OpenSpec на машину, вернуться по симптому „третий раз
   объясняю“»** — симптом лечится строкой в `AGENTS.md`, не спекой. Ставить
   нечего.
6. **«Kiro Review mode»** — такого режима нет (Supervised mode / spec review
   screen); к делу не относится.
7. **«Свежая сессия — когда одна начнёт уставать»** — усталость изнутри не
   видна ни агенту, ни владельцу с телефона. Правило должно быть тупым:
   сессия живёт до слияния PR среза.
8. **Раскладка `docs/arc42/…`** — см. 2.3: слоты да, номера нет.

## 4. Семь вопросов

1. **OpenSpec — не брать, не ставить.** Валидатор структурный; дрейф не
   решён; brownfield-first; в одной сессии с мелкими срезами контекст между
   сессиями — это репозиторий, PR и ADR. Условие вернуться: срез не влезает
   в один PR и задевает больше двух модулей — тогда `docs/notes/<дата>-план-
   <срез>.md` руками (идея GSD), всё равно без инструмента.
2. **Свой опросник, тело — `orch/prompts/role-conventions.md`.** Он уже
   написан по регламенту Red Hat (≤150, свидетельства, один пакет вопросов).
   Доработать три вещи: проверять командой каждую команду, которую записал;
   порядок вопросов по частоте промахов (как в брифе §5); режим повторного
   прохода «сверь файл с кодом, предложи, что выкинуть». Memory Bank — нет.
   Оформить как скилл `project-init` в `.agents/skills/` (+ симлинк
   `.claude/skills`).
3. **EARS — нет.** Критерии приёмки свободным текстом, но с одним
   требованием: каждая строка — проверяема и становится одним тестом
   (правило хабровского соло-разработчика, без его ledger'а). Таблица вместо
   EARS там, где это автомат состояний или матрица прав.
4. **Свежая сессия — сразу, правилом «сессия = срез до слияния PR».** В AoE
   это бесплатно. План на многошаговый срез — файл в `docs/notes/` или
   описание PR, читается следующей сессией.
5. **Первый заход — ядро + четыре сторожа из 3.4.** Compound-петля без
   плагина (правка `AGENTS.md` тем же PR под сторожем размера) — это часть
   ядра, а не второй шаг. Всё остальное (jscpd как блокирующий,
   dependency-cruiser, ревьюер в свежей сессии) — по симптому.
6. **`project new`** — три варианта:
   - (рекомендую) `project new <имя> [--like <проект>] [--no-github]`:
     каталог в `/projects`, `git init`, скелет из `files/skeleton/`
     (`AGENTS.md`-каркас, `CLAUDE.md`, `docs/README.md`, `docs/decisions/`
     с шаблоном, `docs/concepts.md` с пустыми строками забот, `.oneway`,
     четыре адаптера хуков, `scripts/check-agents-size.sh`,
     `check-doc-paths.sh`, `check-pr-shape.sh`, `guard-oneway.sh`, `.github/
     workflows/ci.yml` с этими шагами), `--like` копирует allowlist из живого
     проекта (`scripts/check-*.sh`, `tests/Arch/`, `pint.json`,
     `phpstan.neon`, `Makefile`, `docker-compose.yml`), затем `ports claim
     --from-compose` и `gh repo create --private`. Живой проект — шаблон,
     отдельного шаблона стека поддерживать не надо.
   - Голый каркас без стенда и GitHub: меньше кода, но второй шаг всё равно
     делается руками каждый раз.
   - Стек-шаблоны в `files/templates/laravel/`: чище, но это вторая копия
     `listate-crm`, которая разойдётся.
7. **Стек не назван — план разделён на две части.** Стеконезависимое
   (`AGENTS.md`, слоты `docs/`, хуки, три sh-сторожа, jscpd) — делается
   сейчас. Слой arch-правил — по стеку: PHP — Pest arch (есть) + sh-grep;
   TS/Vue — dependency-cruiser (`.vue` подтверждён), ESLint заводить только
   вместе с первым правилом границ; Python — import-linter; Go —
   go-arch-lint; .NET — ArchUnitNET. Если новая система — Laravel + Inertia +
   Vue как `listate-crm`, всё берётся через `--like`.

## 5. План для vps-dev

### 5.1. Раскладка документации проекта (единые слоты)

```
AGENTS.md              ≤200 строк; правило = строка со ссылкой на сторож или ADR
CLAUDE.md              @AGENTS.md
docs/README.md         карта: чему верить, в каком порядке, чего здесь нет
docs/concepts.md       каркас: забота → пример в коде (путь) → правило → сторож;
                       первой строкой парадигма; пути проверяет CI
docs/decisions/        ADR: README с правилами, 000-template.md, NNN-*.md
docs/<тема>.md         замысел по темам (как в listate); «Решено» дублируется в ADR
docs/notes/            снимки: <дата>-<о чём>.md, не поддерживаются
scripts/check-*.sh     сторожа; каждый объясняет в шапке зачем и чего не ловит
.oneway                маски необратимого для guard-oneway.sh
.agents/skills/        скиллы проекта; .claude/skills → симлинк
```

Скелет `AGENTS.md` — заголовки в порядке частоты промахов: проверить себя ·
поднять · стоп-лист · где что лежит (с примером) · стек и чего не брать ·
стиль решений (таблица «что за данные → чем») · линт/формат · git · не
трогать. Под каждым — 3–15 строк, пример строки правила:
`- Домен не знает про HTTP — tests/Arch/ArchitectureTest.php:91`.

### 5.2. Ворота в CI под Laravel/Vue (что добавить к `listate-crm/ci.yml`)

Есть: Pint, PHPStan max, Peck, `check-boundaries`, `check-comments`,
`check-migrations`, миграции на чистой базе, `vue-tsc`, сборка, Pest (Arch,
Unit, Feature, Browser), покрытие типами 100 %, лицензии, standalone-сборка.

Добавить в задачу `checks` и в `make lint`:

1. `scripts/check-agents-size.sh` — `AGENTS.md` ≤ 200 строк.
2. `scripts/check-doc-paths.sh` — пути в бэктиках из `AGENTS.md` и
   `docs/**/*.md` существуют относительно корня; `путь:N` — N ≤ строк файла;
   `vendor/` в ссылках запрещён. Сначала как предупреждение на `docs/`,
   блокирующий на `AGENTS.md`.
3. `npx jscpd app resources/js --threshold <N> --ignore "**/migrations/**"` —
   первый прогон без порога, N выбрать по факту.

Отдельная задача `pr-shape` (только `pull_request`):

4. `scripts/check-pr-shape.sh origin/main`: `app/**` ⇒ `tests/**`;
   `composer.json`/`package.json` (секции зависимостей) ⇒
   `docs/decisions/**`; `database/migrations/**` ⇒ в теле PR есть
   `@одобрено` (через `gh pr view --json body` или `$GITHUB_EVENT_PATH`).

В arch-тесты — по мере постройки забот, каждая как запрет:
`arch('страницы не ходят в БД')->expect('App\Http\Controllers')->toOnlyUse([...])`
слишком широко; брать точечные `not->toUse`, как уже сделано. Контракт
значений (`from`/`tryFrom`/`value`) — дописать в существующий тест
«значения реализуют общий контракт» через `ReflectionClass`, после чего
абзац 345–359 из `AGENTS.md` удалить.

Фронт: dependency-cruiser с одним правилом «`resources/js/pages/**` не
импортирует `axios` и не зовёт `fetch` мимо `resources/js/support/`» — когда
появится вторая страница с данными. ESLint — только вместе с ним.

### 5.3. Хуки «стоп перед необратимым»

`scripts/guard-oneway.sh <путь>`: читает `.oneway`, при совпадении выходит
с кодом запрета и текстом «необратимое место: спроси владельца; после ответа
— строка `@одобрено <дата> <что>` в описании PR». Адаптеры в скелете:

- `.claude/settings.json` → `hooks.PreToolUse[{matcher:"Edit|Write",
  command:"scripts/guard-oneway.sh"}]`, путь из `tool_input.file_path`;
- `.codex/hooks.json` → `PreToolUse`, путь из текста `apply_patch`
  (`*** Update File:`); **проверить при внедрении**;
- `.gemini/settings.json` → `BeforeTool`, matcher `write_file|replace`,
  ответ `{"decision":"deny","reason":…}`;
- `.opencode/plugin/guard.ts` → `tool.execute.before`, `throw` для
  `edit|write|apply_patch`.

Проверка каждого адаптера — руками, один раз: попросить агента поправить
миграцию и увидеть отказ.

### 5.4. Что править в vps-dev

**Роль `style`** (`ansible/roles/style/`):

- `templates/work-slice.md.j2`, `work-docs.md.j2`, `work-gates.md.j2` →
  `/var/lib/vps-dev/style/work/{slice,docs,gates}.md`, loop как у
  `machine-*`. Каждый ≤ 40 строк, первая версия — из практики
  `listate-crm`, не из теории:
  - `slice.md`: срез = один PR = одна сессия; тест первым коммитом; перед
    кодом — список задетых забот из `docs/concepts.md`, «не построена» →
    каркасный PR отдельно; стоп-лист по `.oneway`; описание PR: что, зачем,
    заботы, `@одобрено`.
  - `docs.md`: слоты из 5.1, четыре класса по сроку жизни, «правило требует,
    решение датировано, снимок помечен датой»; что можно писать в
    `AGENTS.md`, а что нет (правило без сторожа или ADR — не пишется).
  - `gates.md`: список общих сторожей, как добавить свой (шапка «зачем / чего
    не ловит», падение на пустом множестве).
- Второй блок `blockinfile` в общий промпт с маркером «метод, пишет
  выкатка» и тремя строками-оглавлением (`work/slice.md` — как резать и
  сдавать; `work/docs.md` — куда класть; `work/gates.md` — чем проверяется).
- Ключ `context.fileName: ["AGENTS.md","GEMINI.md"]` в
  `~/.gemini/settings.json` — той же механикой, что `outputStyle` у Claude.
- Каталог `/var/lib/vps-dev/style/skills/<имя>/SKILL.md`, ссылки
  `~/.agents/skills` (Codex, Gemini) и `~/.claude/skills` → на него.
  Глобальный путь OpenCode для скиллов — уточнить при внедрении (не
  проверял). Скиллы: `project-init` (из `role-conventions.md`),
  `skeleton-talk` (каркас: список забот по типу приложения → пакеты с

  ADR; ничего не строит), `docs-tidy` (инвентаризация `docs/`, раскладка по
  слотам, проверка дешёвых утверждений, вытаскивание «Решено» в ADR, спорное
  в `docs/notes/archive/`). Каждый ≤ 150 строк.

**Новая роль `project`** (по образцу `ports`): `files/project` — bash-CLI
`project new` из вопроса 6; `files/skeleton/` — файлы из 5.1 и 5.3;
`tasks/main.yml` — копия в `/usr/local/bin/project` и скелета в
`/var/lib/vps-dev/project/skeleton/`. README: раздел «Первый проект» → одна
команда.

**README** — раздел «Как здесь ведут разработку»: два режима (сессия —
владелец читает каждый PR; оркестратор — решения доверены агенту), общие
для обоих `AGENTS.md`, сторожа, хуки; ссылка на `style/work/`.

**orch** — ничего срочного: сторожа в CI проекта распространяются на PR
цепочки сами. Копилку Наладчика разобрать один раз: про инструмент —
остаётся в orch, про проект — строками в `AGENTS.md` проекта под сторожем
