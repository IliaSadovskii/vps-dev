# Побочные роли: архитектура

Спецификация надстройки над `PLAN.md`. Побочная роль — агент, у которого
есть область, повод проснуться, ход и выход, но **нет места в графе
цепочки**. Первые четыре: Стенд (уже работает, переезжает сюда), Наладчик,
Тимлид, Библиотекарь. Замысел и решения владельца — в конце файла.

Три требования, из которых выведено всё остальное:

1. Новая роль добавляется **описанием, а не кодом движка**. Движок знает
   про «побочную роль вообще», а не про Наладчика.
2. Правила `PLAN.md` §2 не ослабляются: единственный писатель базы —
   движок, реконсиляция вместо событий, идемпотентность, ничего не
   додумываем.
3. Отказ любой побочной роли не задевает прогон. Она наблюдает и
   советует; работу делают шаги цепочки.

## 1. Описание роли — файл, а не код

`asides/<имя>.yml`, рядом с `chains/*.yml`, читается так же и так же
проверяется на старте.

```yaml
name: tune                     # Наладчик
scope: run                     # run | task | project | machine
workspace: repo:~/projects/vps-dev   # task | none | repo:<путь>
icon: "🔧"                     # знак роли в титуле её сессий
rights: [read, hold, patch, pr]
budget: { runs_per_task: 20, max_live: 1, cost_usd: 5 }

wakes:                         # поводы проснуться, по одному ходу на повод
  - on: run_started
    prompt: role-tune-start
    session: fresh             # shared (общая переписка) | fresh (своя на повод)
    run: { agent: claude, model: sonnet, effort: low }
  - on: run_ended
    prompt: role-tune-review
    session: fresh
    run: { agent: claude, model: "opus[1m]", effort: medium }
  - on: note_decided           # владелец ответил на находку
    prompt: role-tune-apply
    run: { agent: claude, model: "opus[1m]", effort: medium }
```

Добавить роль = положить yml и промпты. Ни строчки в движке.

`session` у повода разводит разбор и разговор. Промпт в занятую сессию AoE
доставляется мосту как `steer`, а тот доставляет его с приоритетом «сейчас»,
то есть **обрывает** текущую генерацию (`src/acp/dispatch.rs`,
`claude-agent-acp`). Пока разбор и разговор жили в одной переписке, движок
рвал разговор владельца с ролью, а реплика владельца — идущий разбор (T26).
Поэтому длинные поводы идут каждый в свою сессию (`fresh`; всё, что должно
дожить до сводки, роль кладёт находкой), а поводы, адресованные разговору (ответ на находку, сводка),
приходят в общую переписку и **ждут**, пока в ней не кончится ход: повод не
теряется, курсор через него не переступает.

Сессия `fresh` живёт один повод: как только ход сдан и переписка освободилась,
движок отправляет её **в архив**. Иначе за прогон их набегает по две на шаг и
сайдбар зарастает так, что живой работы в нём не видно (T26). Ничего при этом
не теряется: находки и лента лежат в базе, а сводку в конце
прогона собирает общая переписка, которая не архивируется никогда.

Знак роли (`icon`) уходит в титул её сессий: `🔧 T35 · Наладчик`, у повода
со своей сессией — `🔧 T35 · Наладчик · шаг закончил ход`. Порядок тот же,
что у сессий шагов (`T35 · plan`): номер задачи первым. Строка
роли стоит в группе задачи вперемешку со строками шагов, и без знака её от
шага не отличить; бейдж на строке говорит второе — имя роли, а пока идёт
ход, повод.

Общая переписка заводится вместе с первым ходом роли на задаче, а не первым
поводом `session: shared`. У Наладчика такой повод — конец прогона, и без
заводки роль весь прогон не видна в сайдбаре вовсе: карточки разбора уезжают
в архив, как только ход сдан. В заводку уходят общие правила роли и одна
строка о том, где что происходит: первое слово владельца иначе прилетело бы
агенту, который не знает ни кто он, ни как отвечать движку. Поводы в эту
переписку правила не повторяют (`aside.greeted_at`).

Роль с областью «прогон» или «задача» кончается вместе с задачей: на уборке
(`archive_old`, через `ARCHIVE_AFTER_H` после конца) её запись закрывается,
а переписки уезжают в архив. Иначе `live`-запись висит вечно, а сайдбар
копит по одной карточке роли на каждую прошедшую задачу. Роли «проект» и
«машина» переживают задачу по замыслу.

У повода есть флаг `attention`: закончив такой ход, роль зовёт владельца
пушем AoE (`notify_on_idle`). Стоит он ровно на сводке конца прогона — её
владелец обязан прочитать; на остальных ходах пуш был бы на каждый шаг.

## 2. Шина: таблица `event` уже ею является

Движок пишет события с монотонным `event.seq`. Побочная роль — подписчик:
на проходе движок читает события старше своего курсора, сверяет `kind` с
`wakes[].on` и заводит побочный ход.

```
reconcile()
  take_inbox()            # заявки снаружи, включая решения владельца
  promote_queue()
  sessions = aoe.sessions()
  for task in live: step_task()      # как сейчас
  pump_asides(sessions)              # ← новое: события → побочные ходы
  archive_old()
```

Курсор двигается **в той же транзакции**, в которой создана запись
побочного хода. Падение между проходами не теряет повод и не дублирует
его. Побочные ходы разбираются последними: шаг цепочки всегда важнее
наблюдателя.

Чтобы шина была полной, движок обязан писать события на все узловые
моменты: `run_started`, `run_ended`, `gate_opened`, `note_decided`.

**Сторож** — дешёвая механика движка, без модели: он только публикует
событие, думает агент. Живёт один — `watch_file_clash`: две задачи полезли
в один файл. Остальные (ход дольше порога, ход дороже порога, файл вне зоны
шага) сняты решением владельца 2026-09-10: Наладчик и так разбирает каждый
ход, а пороги пришлось бы держать в согласии с ценами и размером задач.

## 3. Схема базы

```sql
aside        id, name, scope, scope_key, status, created_at, ended_at
             -- scope_key: id задачи | путь проекта | 'machine'
             -- status: live | done | failed
aside_run    id, aside_id, wake, cause_seq, session_id, started_at,
             prompt_sent_at, ended_at, outcome, cost_usd
aside_note   id, aside_id, task_id, severity, title, body, options,
             state, channel_msg, decision, decided_at
             -- severity: hold | fyi
             -- state: open | sent | answered | applied | dropped
aside_cursor name, scope_key, seq
```

`aside` заменяет поля `stand_*` в `task`: миграция переносит живые стенды
и снимает три колонки. Обобщение сразу проверяется на том, что уже
работает.

Ключ идемпотентности сессии: `aside/<name>/<scope_key>/<wake>/<cause_seq>`.
Повтор прохода не создаёт вторую сессию, как и у шагов.

## 4. Находка — единственный выход наружу

Всё, что побочная роль хочет сказать владельцу, — запись `aside_note`:
что случилось, почему подозрительно, варианты. Варианты не произвольный
текст: под каждым лежит глагол из фиксированного словаря, который умеет
исполнить движок.

| Глагол | Что делает |
|---|---|
| `continue` | ничего; всегда первый и по умолчанию |
| `restart` | отменить заход и начать шаг заново |
| `back:<шаг>` | вернуть задачу на шаг |
| `say:<текст>` | передать реплику владельца роли |
| `stop` | остановить задачу на владельце |
| `patch` | разрешить роли применить свою правку |

`severity: hold` — задача замирает до ответа. `fyi` — прогон едет дальше,
находка ждёт в сводке. Выбор веса — единственное решение, которое роль
принимает сама.

## 5. Права проверяет движок, а не промпт

Словарь: `read`, `hold`, `move`, `patch`, `pr`. Проверка на входе
`orch aside …` по `asides/<имя>.yml`. Промпт можно уговорить, движок —
нет. Роль без `move` не сдвинет задачу, даже если очень захочет.

## 6. Как роль говорит с движком

Тем же путём, что и все: файл-заявка в `inbox/`, писатель один.

```sh
orch aside note --id A17 --hold --title "…" \
     --option continue:"оставить как есть" \
     --option restart:"перезапустить шаг реализации"
orch aside done --id A17 [--outcome …]
orch aside pr --id A17 --branch tune/T42-prompts
```

Опознание — по `--id` и `--pass`: номер хода плюс пропуск, который движок
печатает в промпте. Одного номера мало — это маленькое целое, и без секрета
любая сессия могла бы остановить любую задачу.
Через каталог, как у шагов (`taskdir.py`), нельзя: рабочая копия у
Наладчика общая на все его заходы, а окружение AoE обычным сессиям не
передаёт (`research/RISKS.md` п. 1). Движок сверяет id с живым `aside_run`
и отвергает чужой.

## 7. Рабочая копия побочной роли

- `workspace: task` — копия задачи, только чтение (Тимлид, Библиотекарь).
- `workspace: none` — копии нет (машинные роли).
- `workspace: repo:<путь>` — готовый каталог: для Наладчика это **живое
  дерево** vps-dev, потому что только там правка подействует на текущий
  прогон (движок читает промпты и цепочки оттуда).
- `mirror: worktree:<проект>` — вторая копия того же проекта под коммиты.

Разделение живого дерева и копии под коммиты нужно потому, что в живом
дереве лежит незакоммиченная работа владельца: правка туда, коммиты — в
свою ветку, один PR на прогон, сливает владелец руками. Прогон при этом
перестаёт быть воспроизводимым — осознанная цена (решение 2026-09-07):
починить промпт сейчас важнее, чем сохранить чистоту показаний, а по
сообщению коммита видно, на каком шаге текст поменялся.

## 8. Скелет хода — `digest.py`

Разбирать сырой транскрипт моделью дорого: у Реализации это сотни тысяч
токенов. Отдельный модуль без зависимостей от движка читает
`~/.claude/projects/<путь-копии>/<сессия>.jsonl` за окно захода и отдаёт
компактный обзор: вызовы инструментов с целями и кодами возврата, ошибки,
тронутые файлы, вопросы и ответы владельца, финальное сообщение, время и
стоимость. Модель читает обзор и лезет в сырой текст только там, где не
сходится.

Чистая функция на фикстурах — самая тестируемая часть надстройки.

## 9. Транспорт: `notify.py` + `telegram.py`

Движок знает про `Notifier` с реестром каналов, а не про Telegram.

```python
class Channel(Protocol):
    def send(self, note) -> str | None: ...      # id сообщения или None
    def poll(self) -> list[dict]: ...            # решения владельца
```

Каналы: `panel` (всегда, рисует блок находок в панели задачи) и `telegram`
(если настроен токен). Long polling изнутри воркера — наружу порт не
открывается. Список `chat_id` жёсткий: токен даёт право нажимать кнопки.

Входящее нажатие → заявка `{kind: "note_decision", note, option}` в
`inbox/`. Повторное нажатие отклоняется по `state`, как устаревшая кнопка
отклоняется по ревизии. Не доставили — находка остаётся `open` и уйдёт
следующим проходом; доставили — `channel_msg` не даёт послать дважды.

Первая польза от канала не связана с побочными ролями: в него же уходят
обычные ворота задачи. Это проверяет транспорт до появления агентов.

## 10. Предохранитель одновременности

`max_running = 3` считает **задачи**, а не сессии, и побочные роли его
обходят — отсюда падения тестов по памяти. Добавлен `max_sessions`: предел
одновременно **работающих** сессий AoE (шаги, стенды, побочные роли), плюс
порог свободной памяти перед стартом любой сессии. Считаются именно
работающие: сессия в `Idle` висит до архивации неделю и почти ничего не
стоит, а память ест ход агента. При нехватке ход не заводится и ждёт
следующего прохода; шаг цепочки в приоритете, из побочных — сначала `hold`.

Событие конца захода пишет сама `Db.end_run`, а не пять мест движка: забыть
его в новом месте закрытия было бы нечем поймать.

## 11. Роли в этой схеме

| Роль | scope | Поводы | workspace | Права |
|---|---|---|---|---|
| Стенд | task | задача встала, задача закрыта | task | read, patch |
| Наладчик | run | старт захода, конец захода, сторожа, решение владельца, конец прогона | живое дерево vps-dev + своя ветка | read, hold, patch, pr |
| Менеджер проекта | project | задача доведена до конца или снята | копия задачи + своя копия проекта | read, patch, pr |

Сисадмин в orch не живёт: он про машину, а не про оркестратор. Отдельный
модуль vps-dev, общий с orch у него только транспорт.

**Тимлид отменён (2026-09-07).** Замысел был в том, чтобы отвечать роли
вместо владельца на обратимом и ловить дрейф от ТЗ. Оба основания не
устояли: ворота стоят там, где владелец боится чужого решения, и подставлять
туда ещё одного агента на той же модели незачем; ТЗ и так лежит в блоке
задачи у каждого шага, а сделанное с ним сверяют Ревью кода и PR. Из всего,
что ему приписывалось, не покрытым осталось одно — соседние задачи, — и это
факт, а не суждение: его считает сторож `watch_file_clash` git-ом, без
модели. Право `answer` снято из словаря вместе с ролью.

Менеджер проекта — бывший Библиотекарь с двумя шляпами: итог законченной
задачи (что решили, что отвергли — предложением в документацию проекта
отдельным PR) и сверка бэклога с тем, что задача сделала (заявка закрыта заодно, ссылается
на исчезнувшее устройство, потеряла основание). Он ничего не решает и
никого не двигает.

**Копилки сняты (2026-09-09).** У ролей была своя память между прогонами:
файл рядом с базой, куда роль дописывала строки (`memory: machine|project|
task`, право `memory`, команда `orch aside memory`), а копилка Менеджера
вклеивалась хвостом в 6000 знаков в **каждый** промпт **каждого** шага
следующих задач проекта («Память проекта»). Сняты по трём причинам:

- внутри прогона она дублировала находки, которые и так лежат в базе,
  показываются в панели и собираются сводкой;
- между прогонами она распухала без всякого удержания: единственным
  ограничением была обрезка по длине, то есть терялось самое старое, а не
  самое бесполезное, и каждый ход платил контекстом за чужие заметки;
- проверить её было нечем: свободный текст, устаревающий молча.

Вместо неё: **находки** (в базе, с ответами владельца) — память в пределах
задачи, и они же отдаются сводке роли по прошлым задачам (`history: 15` у
повода). **Документация проекта** — всё, что должно пережить задачу:
Менеджер открывает PR, владелец решает. Не созрело до документа — не помним
вовсе, и это осознанная цена.

## 12. Настройка: страница «Агенты»

Свежая машина приезжает с **выключенными** побочными ролями. Это не
украшение: чужой человек, развернувший такой же сервер, не должен получить
агентов, которые сами кому-то пишут и что-то коммитят. Включение —
сознательное действие на странице.

Механика повторяет страницу «Цепочки», которая уже работает: заводской
файл в репозитории (`asides/<имя>.yml`) не трогается никогда, правки
владельца ложатся рядом с базой (`~/.local/share/orch/asides/<имя>.yml`),
«Сбросить до заводских» = удалить пользовательский файл. Так правки не
засоряют `git status` рабочей копии и не уезжают в чужие коммиты.

Страница — соседняя вкладка к «Цепочкам», строка на роль:

| Что | Где живёт | Правится |
|---|---|---|
| Включена или нет | `enabled` в пользовательском yml | переключателем |
| Модель и усилие по каждому поводу | `wakes[].run` | выбором из каталога моделей |
| Бюджет: ходов на задачу, живых сессий, потолок в долларах | `budget` | цифрами |
| На каких цепочках | `chains: [deep, blueprint]` | галочками |
| Права | `rights` | **только чтением**; меняются правкой файла |

Права на странице не редактируются намеренно: это контракт безопасности, а
не настройка вкуса. Случайно выдать роли `pr` кнопкой не должно быть
возможно.

Признак «включена» живёт в yml роли, а не в настройках плагина: настройки
плагина плоские и объявляются в манифесте заранее, значит каждая новая роль
требовала бы правки манифеста. В манифесте остаётся только то, что не
растёт: общий выключатель побочных ролей, `max_sessions`, порог памяти.

**Три уровня, чтобы не запутаться:** включение — на машине (страница),
применимость — в цепочке (`chains:` в yml роли), исключение — на задаче
(флажок в листе автономии, как `stand_wanted` сейчас).

### Привязка Telegram — внутри интерфейса, без ручных секретов

Токен нигде заранее не зашивается и в репозиторий не попадает. Панель не
умеет полей ввода, но у AoE есть `composer-action` + `composer.read`:
кнопка рядом с полем ввода читает то, что человек в него вставил. Это
единственный документированный способ получить свободный текст без участия
модели, и он же — способ ввести токен.

1. На странице «Агенты» — «Привязать бота». Вставляешь токен в поле ввода
   любой сессии, жмёшь кнопку. Движок кладёт его в
   `~/.local/share/orch/secrets.json` с правами `0600` и сразу чистит
   черновик (`composer.write`).
2. Движок начинает опрос бота и показывает на странице: «жду сообщения».
   Пишешь боту `/start` со своего телефона — движок ловит первое сообщение
   и предлагает: «Привязать чат такой-то?». Жмёшь — `chat_id` записан.
   Руками id не вводится нигде.
3. «Проверить» шлёт тестовое сообщение с кнопкой. Не дошло — роль,
   которой нужен канал, не включится.
4. «Отвязать» стирает токен и список чатов.

### Роль без канала

Роль, которой канал нужен (`requires: notify` в yml), без привязанного бота
включается **в урезанном виде**: пишет находки только в панель и теряет
право `hold`. Иначе она остановит задачу, а сказать об этом будет некому, и
прогон встанет молча. Полные права возвращаются сами, как только бот
привязан. Библиотекарю канал не нужен вовсе — он ничего не спрашивает.

## 14. Риски

| Риск | Чем закрыт |
|---|---|
| Лавина сессий, нехватка памяти | `max_sessions`, порог памяти, `budget` роли |
| Наблюдатель меняет наблюдаемое | правки только в своей копии, к идущему прогону не применяются |
| Шум в Telegram | `severity`, молчание при чистом ходе, одна строка-сводка в конце прогона |
| Утечка токена бота | жёсткий список `chat_id`, действия только из словаря вариантов |
| Побочная роль зациклилась | `budget`, PR за владельцем, один перезапуск на шаг |
| Побочная сессия умерла молча | `aside_run` без `ended_at` добивается следующим проходом, курсор не двигался |
| Повод пришёл, пока роль занята | курсор через него не переступает: ход заведётся следующим проходом |
| Чужая сессия зовёт `orch aside` | пропуск хода; без него команда отвергается и пишется в журнал |
| Поток мелких PR | один PR на прогон, а не на находку |
| Чужая машина получает агентов молча | по умолчанию всё выключено; включение руками на странице |
| Роль остановила задачу, а сказать некому | без канала роль теряет право `hold` |

## 15. Решения владельца (2026-09-07)

Транспорт Telegram строится первым, Наладчик следом. Наладчик: Sonnet на
проверке входного промпта, Opus на разборе хода; коммитит правки и сам
открывает PR в vps-dev (один PR на прогон). Побочные сессии — общая
таблица, Стенд переезжает сразу. Автономных действий у побочных ролей нет,
кроме права остановить ход. Предел живых сессий — 6. Наладчик включается
на `deep` и `blueprint`. Копилка Наладчика — общая на машину. Побочные роли по умолчанию
выключены; включаются и настраиваются на странице «Агенты», токен бота
вводится через поле ввода и живёт в `secrets.json` рядом с базой.
