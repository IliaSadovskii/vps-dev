# Как устроена передача: карта сверху

Рабочая модель, а не решение. Написана, чтобы было что критиковать: до неё
цепочка правилась точечно, по одной жалобе за раз, и целиком её никто
не смотрел.

Сверено с доской 2026-09-05, вечер. С первой версии изменилось: состояние
задачи уехало из прозы в `state.json` (скрипт `kd-state`), доклад владельцу
пишет автор решения разделом «Для владельца», ворота его публикуют дословно,
вывод прогонов ушёл в `logs/`, входы ролей адресуются разделами, и колонок
стало семнадцать вместо двадцати.

## Кто участвует

- **Владелец** — решает на воротах, отвечает на вопросы, заводит задачу.
- **Роль** — колонка доски: промпт + модель + права. Работает один ход и
  умолкает.
- **Движок Kandev** — двигает карточку, стартует агента, сбрасывает память.
- **Сессия** — чат. Заводится **на модель, а не на колонку**: две колонки на
  одной модели разговаривают в одном чате, на разных — не видят друг друга
  вовсе. Отсюда почти все сегодняшние потери.
- **Диск** — рабочая копия задачи, общая для всех её сессий. Единственное,
  что видят все.

## Куда что течёт

```text
                 ┌─────────────────────────────────────────┐
   владелец ────▶│ текст задачи (создание)                 │
                 │ заметки и ответы на воротах             │──┐
                 │ правка Плана в интерфейсе               │  │
                 └─────────────────────────────────────────┘  │
                                                              ▼
   ┌──────────────────────────── ДИСК ──────────────────────────────┐
   │ .kandev/artifacts/<id>/                                        │
   │   README.md          индекс, стартовый коммит                  │
   │   state.json         выбор, заходы, вердикты, нерешённое        │
   │   logs/<роль>.txt    дословный вывод прогонов                   │
   │   <роль>.md          что роль сделала и на чём стоит           │
   │   notes-<роль>.md    что владелец сказал именно этой роли      │
   │ репозиторий задачи                                             │
   │   AGENTS.md          конвенции проекта (пишет Conventions)     │
   │   docs/knowledge/    описание продукта (пишет Blueprint)        │
   │   код, коммиты с трейлером Kandev-Step                          │
   └────────────────────────────────────────────────────────────────┘
                    ▲                              │
                    │ пишет                        │ читает
                    │                              ▼
              ┌───────────────────────────────────────┐
              │ РОЛЬ: читает перечисленное в контракте │
              │ делает работу, пишет свой файл,        │
              │ делает ровно один переход              │
              └───────────────────────────────────────┘
                    │
                    ▼ (движок)
              ┌───────────────────────────────────────┐
              │ ВОРОТА: публикуют доклад автора дословно,│
              │ спрашивают вариантами-исходами,        │
              │ записывают ответы владельца в          │
              │ notes-<роль>.md, карточку не двигают   │
              └───────────────────────────────────────┘
                    │
                    ▼
                 владелец
```

Три канала «наружу», которые не показаны стрелкой, но существуют: нативный
План Kandev (пишет Planning, читают Plan Review и Test Authoring), панель
ревью Kandev (пишут ревьюеры, читает владелец) и пул-реквест.

## Алгоритм одного хода роли

```text
1. вход        прочитать то и только то, что названо в контракте
               (свой notes-<роль>.md — первым, он новее всего)
2. заход       kd-state lap <колонка> — номер даёт состояние
3. работа      сделать своё; всё, на чём стоит вывод, — из открытых файлов
4. выход       написать свой файл: ответ раньше обоснования
5. переход     ровно один: step_complete вперёд или move_task назад
               (назад — не больше одного раза за заход)
```

## Алгоритм одного хода ворот

```text
1. приход      прочитать «Для владельца» в файле предыдущей роли
2. записка     опубликовать его дословно; своего добавить только вопрос,
               маршрут с последствиями и расписку
3. вопросы     все решения одним вызовом, вариантами
4. разговор    отвечать по файлам; «в файле этого нет» — валидный ответ
5. запись      каждое сообщение владельца → notes-<адресат>.md, дословно
6. расписка    после каждого ответа — список записанного
   ворота не работают, не коммитят и карточку не двигают
```

## Инварианты, которые обязаны держаться

1. **Сказанное владельцем не теряется.** Всё, что он напечатал, лежит на
   диске в файле роли-адресата, и он это видит распиской.
2. **Решение доезжает до исполнителя.** Выбранный вариант читает тот, кто
   его строит, а не только тот, кто предложил.
3. **У факта один владелец.** Роль пишет свой файл и не переписывает чужой;
   на чужое ссылается путём, а не пересказом.
4. **Роль получает всё нужное и ничего лишнего.** Матрица входов — не
   рекомендация, а ограничение расхода.
5. **Один переход за ход.**
6. **Владелец решает, не додумывая.** Всё для решения — в карточке; файлы
   для проверки, а не для понимания.

## Где эти инварианты ломались (замерено сегодня)

| Инвариант | Как сломался | Почему |
|---|---|---|
| 1 | Заметка на воротах не доходила до роли | Канал был чат, а чат — на модель |
| 2 | Выбран B, построен A | Ответ лёг в файл, который исполнитель не читает |
| 3 | Один пробел пересказан в шести файлах | Роль пересказывает предшественника вместо ссылки |
| 4 | 849 строк артефактов на одну задачу | Нет разделения «для решения» и «для проверки» |
| 5 | Сигнал завершения пережил возврат | Платформа не гасит его при переходе |
| 6 | «Принять A» без объяснения, что такое A | Суть оставалась в файле, в карточку шёл путь |

Общее у всех шести: **канал существовал в чьей-то голове, а не в устройстве.**
Инвариант держался тем, что роль поступит правильно, а не тем, что иначе
не получится.

## Что ещё не решено

- **Прерывание посреди цепочки.** Роль спрашивает владельца там, где стоит,
  и работа встаёт до ответа. Часть таких вопросов — предпочтения, их можно
  довезти развилкой до ближайших ворот. Границу «спросить сейчас» и
  «довезти» никто не провёл.
- **Промпт вшит в сессию.** Правка промпта не действует на живые карточки:
  сессия создаётся один раз. Значит выкатка меняет поведение только для
  новых задач, и это нигде не сказано.
- **Уведомления.** Карточка с висящим вопросом ничем себя не проявляет.
- **Ошибка человека при перетаскивании.** Часть колонок закрыта флагом, но
  «в разрешённую, но не ту» утащить можно; заметка тогда лежит в файле роли,
  к которой не поехали.
- **Вкладки сессий подписаны моделями,** а не ролями — и переименовать
  нельзя.

## Чего в этой модели может не хватать

Вопросы, на которые модель не отвечает и на которые стоит посмотреть,
как отвечают другие:

На три из четырёх ответ уже есть, вечером того же дня:

- **Доклад владельцу — не отдельная сущность.** Это первый раздел артефакта
  автора решения; ворота его публикуют. Отдельный докладчик — второй автор,
  то есть дрейф. Так же у Kiro, Copilot и Devin: одобряют сам файл.
- **Предпросмотр «что уйдёт» — это входное письмо следующего шага:** выбранный
  вариант, записи заметок дословно, файлы, которые адресат прочтёт. Промпт
  колонки человеку не нужен.
- **Колонок семнадцать, контекстов восемь.** Отдельный контекст оправдан там,
  где изоляция покупает проверку (Plan Review, два чтения Code Review,
  Fix Review) или гигиену (Research с интернетом); остальные сбросы — цена без
  выигрыша.

Открытым остаётся четвёртое: **где граница «агент решает сам» и «спрашивает»**.
Рабочее правило — спрашивать сейчас, только если ответ меняет действия этого
шага или ошибку дорого откатить; остальное довозить развилкой до ворот. В
промптах оно ещё не проведено.
