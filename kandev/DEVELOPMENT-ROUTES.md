# Маршруты разработки

Три маршрута разной глубины с одинаковым началом и одинаковым хвостом.
Названия колонок оставлены английскими, чтобы естественно смотреться в
интерфейсе Kandev.

## Сейчас на доске одна дорожка

Quick и Standard временно убраны — и с доски, и из `workflows/`. Пока
проектируется сам поток (точки вмешательства человека, циклы доработки,
поведение при возврате карточки), три дорожки означали бы три копии каждой
правки и три расходящиеся версии одного и того же решения.

Работа идёт над `Deep`. Quick и Standard выводятся из него вычитанием колонок
— Standard это Deep без блока решений, Quick это Standard без блока плана — и
будут восстановлены из устоявшегося `deep.yml`, а не поддерживаться
параллельно с ним. В git они есть, восстанавливать их с нуля не придётся.

Всё, что ниже, описывает целевое устройство трёх маршрутов.

## Как это выглядит на доске

Цепочка (workflow) в Kandev — это набор колонок. Задача едет по ним карточкой.
Несколько цепочек показываются на доске дорожками одна под другой, и карточку
можно перетащить не только между колонками, но и в другую дорожку.

```text
Quick     │ Backlog │ Discovery │ Scoping │ Test Authoring │ Implementation │
          │ Verification │ Code Review │ Security Review │ Review Fixes │
          │ Final Verification │ Documentation │ Draft PR │ Human Review │ Done

Standard  │ Backlog │ Discovery │ Scoping │ Planning │ Plan Review │
          │ Plan Approval │ + весь хвост Quick от Test Authoring

Deep      │ Backlog │ Discovery │ Scoping │ Research │ Solution Synthesis │
          │ Solution Approval │ + весь Standard от Planning
```

Начало у всех трёх одинаково: `Backlog` — ручная очередь, где карточка ждёт,
пока вы не двинете её дальше, и есть время дописать условие; `Discovery` —
разведка проекта; `Scoping` — границы задачи. Хвост от `Code Review` до `Done`
тоже одинаков.

## Принцип нарезки

Маршруты отличаются не «важностью» ролей, а тем, есть ли у роли вход.

| Роль | Питается тем, что… |
|---|---|
| Backlog, Discovery, Scoping | всегда есть |
| Research, Solution Synthesis, Solution Approval | есть выбор между решениями |
| Planning, Plan Review, Plan Approval | работа не помещается в один заход |
| Test Authoring, Implementation, Verification | всегда есть |
| Code Review, Security Review | есть диф |
| Review Fixes, Final Verification | ревью что-то нашло |
| Documentation, Draft PR, Human Review | всегда есть |

Пустой вход бывает только у первых двух групп, поэтому убирать можно только их.
**Режется обдумывание, а не контроль качества**: хвост от Code Review до
Human Review одинаков во всех трёх маршрутах.

Признаков на самом деле три и они независимы: есть ли выбор решения, влезает ли
работа в один заход, трогает ли она безопасность. Честно по всем комбинациям
получилось бы восемь маршрутов, поэтому нарезка сделана лесенкой: каждый
следующий маршрут — предыдущий плюс один блок.

`Security Review` в лесенку не ложится: «трогает ли безопасность» с размером
задачи не связано. Правка прав доступа на две строки — Quick по объёму и
обязательный security по существу. Поэтому он стоит во всех трёх маршрутах, а
дешевизну обеспечивает сама роль: сначала копеечная проверка применимости.

## Кто выбирает маршрут

Человек, заводя карточку сразу на нужной дорожке. Отдельной колонки выбора
маршрута нет, и агент по дороге маршрут не меняет.

Прежде был общий вход `Triage` с колонкой `Route Choice`: `Scoping`
заканчивал рекомендацией, карточка вставала и ждала решения. От этого
отказались. Система рассчитана на программиста, который сам понимает, насколько
сложна его задача, — два хода агента ради совета, который он и так знает,
не окупались. Механически рекомендация тоже никем не потреблялась: ни одна
роль не читает поле маршрута, все определяют глубину по наличию входных
файлов (`solution-synthesis.md` есть — значит, был Deep).

`Discovery` и `Scoping` при этом остались и переехали в начало каждой дорожки.
Они нужны не для выбора маршрута: их артефакты — единственное, что знают о
проекте и о границах задачи роли, которым сбрасывают контекст. Без
`discovery.md` `Code Review` не знает конвенций проекта, без `scoping.md` он
не отличает «забыли сделать» от «намеренно не делаем».

Это по-прежнему осознанный отказ от одной дорожки, по которой агент прыгает
через колонки сам. Прыжки технически поддержаны и стоят ноль (пропущенная
колонка не выполняет `on_enter`, её агент не стартует вовсе), но тогда маршрут
нигде не записан: он существует только как текст в промптах, его нельзя ни
увидеть, ни проверить линтом. Здесь маршрут — это сама дорожка.

## Границы контекста

Контекст сбрасывается перед `Plan Review`, `Code Review`, `Security Review`,
`Review Fixes`, а также перед `Test Authoring` в Standard и Deep.

В Quick перед `Test Authoring` сброса нет намеренно: в контексте лежат только
`Discovery` и `Scoping`, и перечитать репозиторий заново дороже, чем донести
уже собранное. В Standard и Deep к этому моменту в контексте лежат Planning и
Plan Review, тащить их в реализацию дороже, чем перечитать план.

## Почему такой порядок

- `Discovery` изучает правила, документацию и структуру проекта до всякого
  обсуждения вариантов, чтобы не спрашивать о том, что уже написано в
  репозитории. Его артефакт читают все роли со сброшенным контекстом.
- `Scoping` определяет границы задачи после знакомства с проектом: что входит,
  что намеренно нет и почему, что принято на веру. Маршрут он не выбирает.
- `Research` сначала отсеивает мнимые развилки, потом ищет по оставшимся —
  именно по их критериям, а не по теме вообще. Отбор идёт до поиска: поиск,
  запущенный раньше списка, расползается в общий дорогой обзор, а развилка,
  записанная после поиска, подгоняется под найденное.
- `Solution Synthesis` сводит локальный контекст и внешние данные в один вариант.
- `Planning` создаёт план, `Plan Review` проверяет его свежим взглядом до
  человеческого `Plan Approval`.
- `Test Authoring`, `Implementation` и `Verification` идут в одном контексте.
  Шаг называется Authoring, а не Design, потому что обязан оставить реально
  падающие тесты: документ с описанием тестов ничем не обеспечивает test-first.
- `Code Review` и `Security Review` получают свежие контексты и читают hand-off
  артефакты, поэтому не полагаются на самооценку автора.
- `Review Fixes` выполняется один раз и может быть пустым. Дополнительный круг
  делается ручным возвратом на нужную колонку: счётчика кругов в Kandev нет,
  и ограничить их можно только промптом плюс вашим глазом на доске.
- Первая `Verification` и `Final Verification` — разные работы и потому имеют
  разные промпты. Первая замыкает red-green в контексте реализации, вторая
  работает в контексте `Review Fixes` и гоняет полный прогон после правок.
- `Documentation` идёт после `Final Verification`, в её же контексте: правки
  по ревью уже улеглись, прогон зелёный, и документацию имеет смысл править
  по итоговому коду, а не по промежуточному. Её работа — прежде всего чинить
  разошедшееся с кодом; писать новое она имеет право только там, где проект
  и так документирует такие вещи.
- После `Documentation` создаётся draft PR. Нативный PR/MR auto-fix не
  является шагом цепочки: это переключатель на самой задаче, и включить его
  должна роль `Draft PR` через `update_task_pr_automation_kandev`.

## Transition safety

Каждый автоматический шаг использует `auto_advance_requires_signal: true`.
Переход выполняется только после явного вызова `step_complete_kandev` агентом.
Обычное завершение ответа, вопрос пользователю, ошибка или остановка на
незаполненном prompt не продвигают задачу. Отмена агента также не считается
успешным завершением.

`Backlog`, `Solution Approval`, `Plan Approval`, `Human Review` и `Done` не
запускают агента сами: продолжение требует решения человека.

Доработка делается вручную: написать замечание в задаче и перетащить карточку
назад — с `Solution Approval` на `Solution Synthesis`, с `Plan Approval` на
`Planning`, с `Human Review` или `Done` на `Review Fixes`. Вход в колонку
перетаскиванием запускает её `on_enter`, поэтому агент стартует сам, а роли со
сброшенным контекстом находят замечание в разговоре задачи. Все шаги разрешают
ручное перемещение, так что вернуть карточку можно на любую колонку.

Роль может и сама спросить: `ask_user_question_kandev` задаёт вопросы с
вариантами ответа, и платформа держит карточку, пока на них не ответят —
неотвеченный вопрос блокирует переход. Это разрешено `Scoping`, `Research` и
`Planning`: там ответ бывает только у человека. В технической части нет —
там догадка проверяется тестами.

Между остальными соседними шагами контекст сохраняется. Свежие роли получают
результаты предшественников через artifact protocol.

## Artifact protocol

Workflow-level prompt `@custom-artifact-protocol` будет общим контрактом для
всех ролей. Пока он является безопасной заглушкой и будет подробно написан на
этапе проектирования prompts.

Отдельного шага `Artifact Setup` нет: он тратил бы отдельный agent turn только
на создание каталога. `Discovery` инициализирует manifest в начале каждой
дорожки, а каждая последующая роль проверяет его наличие и создаёт минимальную
структуру, если карточку внесли в маршрут мимо первых колонок.

Для обычной задачи с одним основным репозиторием рабочий каталог имеет вид:

```text
.kandev/artifacts/<full KANDEV_TASK_ID>/
  README.md
  discovery.md
  scoping.md
  research.md
  solution-synthesis.md
  plan-review.md
  test-authoring.md
  verification.md
  code-review.md
  security-review.md
  review-fixes.md
  final-verification.md
  documentation.md
  pull-request.md
```

Имя файла совпадает с именем колонки и не содержит номера: одна и та же роль
стоит в трёх маршрутах на разных позициях, и нумерация разъехалась бы.

Полный `KANDEV_TASK_ID`, который Kandev внедряет в task environment, является
устойчивым ключом. Придуманный slug или заголовок задачи хранится для чтения в
`README.md`, но не используется как идентификатор: заголовок может измениться,
а сгенерированные имена могут столкнуться.

`README.md` служит индексом: task title, workflow, исходный commit, список
созданных artifacts, их статус и зависимости. Каждый шаг владеет своим файлом,
читает только перечисленные входы и не переписывает чужие результаты. Artifact
создаётся только при содержательном результате; обязательные пустые файлы лишь
расходуют токены и создают ложное ощущение завершённости.

Это рабочая память, а не часть продукта. Если проект сам не решил хранить её в
Git, `Discovery` добавляет `.kandev/artifacts/` в локальный Git exclude, не
изменяя версионируемый `.gitignore`. Перед завершением решения, которые должны
пережить task workspace, переносятся в проектные docs, ADR или PR description.
Секреты, полные environment dumps и credentials в artifacts не записываются.

Kandev Plan остаётся единственным source of truth для утверждённого плана:
`Planning` собирает в него решение, границы, риски, этапы и проверки, а свежие
`Plan Review`, `Test Authoring` и `Code Review` читают его через MCP. Писать в
него имеет право только `Planning`: план у задачи один, а
`create_task_plan_kandev` и `update_task_plan_kandev` заменяют его содержимое
целиком, поэтому вторая пишущая роль просто затрёт первую. Review-роли
также сохраняют файловый hand-off; `Code Review` дополнительно вызывает
`publish_review_findings_kandev`, чтобы замечания были видны человеку прямо в
Review UI.

Для multi-repository tasks расположение общего каталога нужно определить
отдельно при написании protocol prompt; текущие маршруты предполагают один
основной repository root.

## Вход в маршрут

Каждый маршрут объявляет стартовой свою колонку `Backlog`, а
`create_task_kandev` принимает `workflow_step_id`. Карточка создаётся в
`Backlog` нужной дорожки и стоит там, пока её не двинут: агент не стартует, и
условие задачи можно дописать. Если начать надо не с начала — например,
разведка по этому коду уже была, — карточку можно создать сразу на любой
колонке. Тогда ответственность за инициализацию артефактов ложится на первую
роль, которая отработает.

## Агентские переходы: что осталось в резерве

Переносимый workflow version 1 не имеет условий по содержанию задачи, её
размеру или результату предыдущего шага. Все переходы в этих файлах безусловны.

Механизм агентского ветвления при этом существует и проверен: роль может
вызвать `move_task_kandev`, и это сочетается с безусловным
`on_turn_complete: move_to_next` без всякого протокола — оркестратор применяет
отложенный агентский move на turn-end и явно пропускает штатную обработку
`on_turn_complete` (`orchestrator/event_handlers_agent.go:668`). Пропущенные
шаги не получают `on_enter`, то есть их агенты не стартуют вовсе.

Он намеренно не задействован. Маршрут, собранный из таких прыжков, нигде не
записан: он существует только как текст в промптах, его нельзя ни увидеть на
доске, ни проверить линтом. Дорожка честнее.

Разумное применение позже — не выбор маршрута, а локальные решения с
проверяемой предпосылкой: например, `Security Review` с нулём замечаний от
обоих ревью может перепрыгнуть пустые `Review Fixes` и `Final Verification`.
Это не суждение о размере задачи, а факт о пустом входе.

Автоматическое разбиение крупной задачи на подзадачи оставлено `Scoping` как
будущая обязанность роли. Сначала нужно определить формат дочерних задач и
место хранения общего решения, иначе трассируемость между частями потеряется.

## Known gaps

Осознанно отложено до этапа адаптивности и prompts:

- Ревью-цикл разомкнут. `Plan Review` при блокирующем замечании всё равно ведёт
  на `Plan Approval`, а после `Review Fixes` независимого повторного ревью нет.
  Замкнуть его статикой нельзя: `move_to_previous` безусловен. Это работа для
  агентских переходов.
- Нативный CI auto-fix правит код уже после всех ревью, и изменённый результат
  цепочкой не просматривается. Для ручного `Human Review` терпимо, для
  автономного режима — нет.
- `Backlog` не запускает цепочку сам. Это осознанная очередь на вход, но
  «создал задачу и ушёл» требует создавать её сразу в `Discovery`.
- Счётчика кругов нет. Повторный проход по ревью делается ручным возвратом, а
  ограничить число кругов можно только промптом и вашим глазом на доске.
- Профили агентов по шагам (`agent_profile`) не заданы. Поле переносимо и даёт
  независимый от состава ролей рычаг стоимости; решение отложено.

## Prompt status

Содержательные prompts на этом этапе намеренно не написаны. Полностью пустой
prompt Kandev импортировать не позволяет, поэтому для каждой новой роли создана
безопасная непустая заглушка. Она сообщает, что роль ещё не настроена, и не
вызывает `step_complete_kandev`; случайно запущенная цепочка остановится на
первом таком шаге.

Все личные prompts имеют префикс `custom-`. Он отделяет их от встроенных и
сторонних prompts и предотвращает незаметные коллизии при импорте.

`custom-ci-fixup` не является линейным шагом workflow: это заготовка для
будущего override встроенного PR/MR auto-fix. Роль `Draft PR` должна будет
включить provider automation через `update_task_pr_automation_kandev` или
`update_task_mr_automation_kandev` после создания и связывания change request.
