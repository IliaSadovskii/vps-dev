# orch: оркестратор ролей поверх Agent of Empires

Сводка решений 2026-09-05 … 2026-09-06. Это спецификация первой версии.
Подробности и обоснования: `research/AOE-CAPABILITIES.md` (что умеет AoE),
`research/STEP-PARAMETERS.md` (откуда параметры шага),
`research/RISKS.md` (узкие места и тесты), `research/DB-NOTES.md` (база).
Роли и цепочки уже написаны под этот формат: `prompts/README.md`,
`chains/*.yml`. Исходный материал лежал в `../kandev/`: доска Kandev с её
ролями и цепочками. Условие «не трогать, пока orch не проведёт одну задачу
Deep целиком» выполнено 2026-09-06, и Kandev снят с машины и из репозитория
вместе с ролями `kandev` и `seed`. Исходный материал ищите в истории git.

## 1. Что это

Цепочка шагов, каждый шаг — роль (промпт + модель + права), задача едет по
шагам, человек решает там, где сам указал. Всё исполнение и весь интерфейс —
Agent of Empires (`aoe serve`, `127.0.0.1:8065`, без токена). Наш код: граф
цепочки, база задач, сборка промптов, содержимое панелей, команда `orch`
для ролей. Ничего своего: ни транспорта, ни интерфейса, ни процессов, кроме
воркера плагина AoE.

## 2. Устройство

Один Python-пакет `orch`, один процесс, четыре роли процесса:

```text
orch-plugin  (воркер плагина AoE, запускает aoe serve)
  ├─ движок:      reconcile() по всем идущим задачам раз в 5 с
  ├─ клиент AoE:  HTTP к 127.0.0.1:8065, никаких WS
  └─ панели:      ui.state.set из состояния базы, клики → движения
orch          (CLI для человека и для ролей; роли зовут done/ask/whoami/push)
```

Правила, которые держат надёжность:

1. **Единственный писатель базы — движок.** `orch` в сессиях базу не
   открывает: пишет файлы в папке задачи и заявки в `inbox/`.
2. **Реконсиляция вместо событий.** Каждый проход: прочитать базу, один
   `GET /api/sessions`, файлы задач; вывести одно действие на задачу;
   выполнить; записать. Старт после падения = первый проход.
3. **Идемпотентность внешних действий.** Сессия создаётся с
   `idempotency_key = task/step/run`; промпт отправляется, только если у
   захода нет `prompt_sent_at`; титул/цвет ставятся всегда (безвредно).
4. **Переход — транзакция с ревизией.** Кнопка несёт ревизию; устаревшая
   отклоняется; двойной клик = одно движение.
5. **Сигнал роли читается только при `Idle`.** Роль может вызвать
   `orch done` и продолжить править файлы — следующий шаг не стартует, пока
   ход не закончился.
6. **Ничего не додумываем.** Ход без сигнала, предел заходов, ошибка →
   красный и кнопки. Таймеров на человека нет.
7. **Порядок записи.** Сначала файлы задачи (`current.json`, промпт), потом
   сессия, потом промпт в AoE. Роль не увидит полузаписанного состояния.

## 3. Данные

### База `~/.local/share/orch/orch.db` (SQLite, WAL)

```sql
task   id, chain, chain_yaml, title, text, project_path, branch,
       worktree_path, group_path, status, human_sheet, revision,
       created_at, closed_at, archived_at
       -- status: backlog | queued | running | waiting | done | closed | abandoned
       --   closed: снята владельцем, работа не делалась
       -- human_sheet: JSON {step: {after: bool|[исходы], ask: bool}} —
       --   лист автономии задачи, заполнен из цепочки, правится владельцем
run    id, task_id, step, n, session_id, context, started_at,
       prompt_sent_at, prompt_sha, ended_at, outcome, start_sha, end_sha,
       duration_s, cost_usd
move   id, task_id, from_step, to_step, actor, trigger, comment,
       artifact_sha, revision, at
       -- actor: agent | human | engine
       -- trigger: outcome:<x> | button | auto | no_signal | max_runs | error | start
event  seq, task_id, kind, payload, at
```

Нет счётчиков (`max_runs` = `COUNT(run)`), нет производных статусов
(«почему ждёт» выводится на проходе). `PRAGMA user_version` + SQL-миграции.

### Папка задачи `.orch/<task>/` в рабочей копии (в `.git/info/exclude`)

```text
task.md            текст задачи (зеркало базы)
chain.yml          замороженная цепочка (зеркало базы)
current.json       {task, step, run, session_id, state}  пишет движок перед промптом
artifacts/*.md     файлы ролей
signals/*.json     {kind: done|ask|note|refused, outcome?, text?, step, run, at}  пишет orch
prompts/<step>-<n>.md   отправленный промпт, дословно
history/<step>-<n>/     копия artifacts/, diff.patch (start..end), log.txt захода
```

`~/.local/share/orch/inbox/*.json` — заявки на новую задачу от `orch task
new`, движок превращает их в строки `task` на следующем проходе.

База — истина о потоке, папка — о содержании. Идентификация задачи в
`orch` — по корню рабочей копии (`git rev-parse --show-toplevel`), не по
окружению: AoE не передаёт переменные окружения обычным сессиям.

## 4. Цепочка

`orch/chains/<name>.yml`, промпты `orch/prompts/` с префиксами типа
(`role-`, `sub-`, `common-`, `skill-`, `test-`; см. `prompts/README.md`).
Структура замораживается при создании задачи, тексты промптов читаются при
каждом старте шага. Цепочку по имени выдаёт `chain.path_of`: если владелец
правил её на странице настроек (шестерёнка на карточке AoE, порт 8073), берётся
`~/.local/share/orch/chains/<name>.yml`, иначе заводской файл репозитория.
Правленая копия собирается страницей из заводской при каждом сохранении, а
кнопка «Сбросить до заводских» её удаляет. И цепочки, и промпты читаются из рабочей копии этого
репозитория (`chain._repo_dir`), а не из установленного пакета: пакет стоит
в venv как editable, и `git pull` на машине меняет тексты ролей для живых
задач сразу, без выкатки. Это удобно для правки промптов и опасно для всего
остального — структуру цепочки живая задача держит замороженной именно
поэтому.

```yaml
name: deep
includes: [common-protocol, common-git-safety]   # общие правила, ко всем ролям
presets:                        # готовые листы автономии (см. §5)
  hands-off: {plan-review.after: false}
  auto: {"*.after": false, "*.ask": false, pr.after: true}
steps:
  - id: plan-review
    run:
      agent: codex              # claude | codex | opencode
      model: gpt-5.6-sol
      effort: high              # необязательно
      mode: full                # только full в v1; plan отклоняется линтером
    prompt:
      file: role-plan-review    # по умолчанию prompts/role-<id>.md
      instructions: "…"         # добавка для этой цепочки
      reads: [plan.md, scoping.md]   # что открыть; движок вклеивает пути
    context: fresh              # fresh | continue
    artifact: [plan-review.md]  # обязан появиться до перехода
    next:                       # строка или исход → шаг; done — конец
      ok: implementation
      rework: plan
    human:
      after: [ok]               # true | false | [исходы]: ждать ли владельца после шага
      ask: false                # true | false: можно ли роли спрашивать владельца в ходе
      moves: [plan, scoping]    # куда владелец может двинуть отсюда кнопкой
    limits:
      max_runs: 3
```

Обязательны `id`, `run.agent`, `run.model`, `next`. Умолчания:
`context: fresh`, `mode: full`, `human.after: false`, `human.ask: true`,
`max_runs: 3`.

Подагенты шага (два чтения ревью) получают **текст** `sub-*.md`: роль-родитель
читает файл по пути из блока задачи и передаёт подагенту целиком вместе с
путями, коммитами и заходом — Claude Code даёт подагенту только то, что
написал родитель.

`context: continue` продолжает **последнюю сессию этого агента в этой
задаче**; нет такой — новая. Другая модель того же агента при `continue` —
`POST /acp/config-option`; отказ → едем на прежней, событие в журнал.

Линтер (при загрузке, в тестах и по замороженным копиям живых задач на
старте): все цели `next`/`moves` существуют, из каждого шага достижим
`done`, исходы уникальны, `max_runs ≥ 1`, `mode == full`, `human.moves`
только с `human.after`, ключи пресетов — существующие шаги. Копия, которую
линтер не читает, красит задачу с причиной; миграций копий нет — новые поля
читаются с умолчаниями.

## 5. Жизненный цикл задачи

**Создание.** Кнопка «Новая задача» в панели «Задачи» (текст из поля ввода
открытой сессии проекта, обычно сессии `Inbox`; поле пустое — последнее
сообщение агента Inbox) или `orch task new --chain deep --project <path>
[--preset hands-off] [--after plan-review=off] [--ask scoping=on]
[--branch <ветка>] [--base <ref>] [--backlog] "текст"`.

`--branch` сажает задачу на названную ветку вместо новой — так дорабатывают
уже открытый PR: ветка есть, движок подключит к ней рабочую копию; ветки нет,
заведёт с этим именем. `--base` говорит, от чего ответвляться, когда ветки
ещё нет (по умолчанию `origin/HEAD`). Ветку, занятую живой задачей, движок не
отдаёт: две задачи писали бы `.orch/` в один каталог и команда `orch` в
сессии не поняла бы, чья она. В панели ветка выбирается ссылкой, а не списком: строка «ветка» переводит
лист в ожидание, владелец вставляет в поле ввода адрес ветки, адрес PR или
просто имя, и кнопка у поля становится «Взять ветку из поля». Списка веток
нет нарочно — поле ввода единственное место, где человек даёт оркестратору
свободный текст, и незачем заводить второе. Занятую ветку панель показывает
красной с именем держателя и не даёт запустить.

Панель перед запуском показывает **лист автономии**:
строка на шаг с двумя переключателями (ворота после, вопросы внутри),
заполнен из цепочки или пресета; щёлкнуть, что нужно, и «Запустить» или
«В бэклог». Лист хранится в `task.human_sheet` и правится в панели задачи в
любой момент для ещё не пройденных шагов. Титул — первые слова; дешёвая
одноразовая модель переименовывает потом (не блокирует).

**Очередь.** Одновременно `running` не больше `max_running` задач
(настройка плагина, по умолчанию 3); остальные `queued` с пометкой в панели.
После лимита провайдера AoE возобновляет каждую сессию сам, движок ничего
не шлёт повторно.

**Старт.** Группа `orch/T12 · <титул>`, ветка `t12-<slug>`. Рабочую копию
задачи делает **движок**, а не AoE: `git fetch origin <база>` (если есть
ремоут), `git worktree add ../<repo>-orch/t12-<slug> -b t12-<slug>
origin/<база>`, `git submodule update --init --recursive` при наличии
`.gitmodules`. Каталог нарочно `<repo>-orch`, а не `<repo>-worktrees`: во
второй папке держит свои копии сам AoE, и его `aoe worktree cleanup` счёл бы
чужие каталоги брошенными. `aoe worktree cleanup` orch не зовёт никогда;
убирает копию тоже движок (`git worktree remove`) — при архиве задачи.

**Все** сессии задачи, включая первую, создаются обычными: `path` — каталог
рабочей копии, `group` — группа задачи, полей `worktree_*` нет вовсе.
Движок сверяет `project_path` ответа с путём копии и падает громко при
расхождении. Причина в интерфейсе: сайдбар веба сворачивает сессии с
одинаковыми `main_repo_path` и `branch` в одну строку-workspace, подписанную
именем ветки (`web/src/hooks/useWorkspaces.ts`), и задача из восьми шагов
превращалась в одну строку без титулов — до сессии прошлого шага было не
добраться. У сессии без ветки ключ строится по её `id`, поэтому каждый шаг
виден отдельной строкой со своим титулом.

Владелец смотрит сайдбар по оси **«по группе»**: заголовок группы —
`orch/T12 · <титул>`, внутри строка на сессию шага. Панель задачи дублирует
этот путь ссылками на сессии заходов.

**Заход шага (reconcile).** Для задачи `running` с текущим шагом:

1. Нет `run` без `ended_at` → создать `run`, записать `move(trigger)`,
   выбрать сессию (`fresh` → создать; `continue` → последняя сессия
   агента), написать `current.json`, собрать промпт → `prompts/` (хеш в
   `run.prompt_sha`), отправить (`POST /acp/prompt`, при `session_transient`
   повтор до 3 раз), титул `T12 · 07 Plan Review`, цвет `amber`,
   `notify_on_idle` по листу автономии.
2. Есть `run` и сессия `Running` → ничего. `Waiting` = вопрос или разрешение:
   если `ask` для шага включён — задача «ждёт ответа в чате», пуш штатный;
   если выключен — `POST /acp/cancel` и промпт «вопросов не задаём: реши сам,
   запиши выбор в `## Допущения`, продолжай», событие в журнал.
3. Сессия `Idle`, в `signals/` файл этого захода:
   - `done` с допустимым исходом, артефакты на месте → `ended_at`,
     `outcome`, `end_sha`, копия в `history/`; если по листу `after` для
     этого исхода → `status: waiting`, цвет `red`, `urgent`; иначе
     `move(outcome)` → следующий шаг или `done`.
   - `done` с ошибкой → `waiting`, причина в панели.
   - `ask` → `waiting`, вопрос в панели; ответ владельца в чате → сессия
     снова `Running`, по `Idle` ищем новый сигнал.
4. Сессия `Idle`, сигнала нет → `ended_at` без `outcome`, `waiting`,
   причина «нет сигнала» плюс последний ответ `orch` из `signals/` (текст
   отказа), кнопки «Продолжай» (промпт «заверши и подай сигнал», один раз
   автоматически), «Принять как готово» (выбор исхода), «Вернуть на …».
   Отменённый кнопкой Stop ход с готовым сигналом и артефактом — обычный
   переход: отмена отменяет ход, не работу.
   Толчок идёт не на первом же проходе. Сначала движок смотрит признак
   жизни мимо AoE: файл транскрипта, который агент пишет сам
   (`run.acp_session_id` — uuid из события `AcpSessionAssigned`, он же имя
   файла). Файл рос последнюю минуту — роль работает, толчка нет вовсе.
   Файла нет — движок отмечает простой и ждёт `IDLE_SETTLE_S`. Промпт в сессию, где ход ещё идёт, AoE доставляет
   как `steer`, а тот **обрывает** генерацию; `Idle` от моста при этом
   бывает преждевременным (T26, 17:57: `Stopped{prompt_complete}` при
   работающей роли — восемь обрывов за прогон устроил сам движок).
5. Сессия `Error` → один раз промпт «продолжай» (событие); всё ещё `Error`
   через полминуты → `waiting`, причина «ошибка». Любой повторный промпт в
   идущий заход («заверши ход», «продолжай», побудка воркера) сдвигает
   `prompt_sent_at`: конец хода считается от последней отправки, иначе
   старый `Idle` сходил бы за новый.
6. Сессии нет → `abandoned`.
7. Перед созданием `run`: заходов шага **на этом круге** не меньше
   `max_runs` → `waiting`, причина «предел заходов», кнопки «Ещё заход»,
   «Принять как есть», «Вернуть». Круг шага начинается, когда работа ушла
   **выше него** по цепочке — кнопкой владельца или исходом роли (Ревью кода
   вернуло задачу в Реализацию): шагу возвращается полный предел, потому что
   он будет читать другую работу. Возврат **на сам шаг** (Правки просят
   перечитать) круг не открывает — от хождения на месте предел и поставлен.
8. Круг, открытый ролью, снимает предел, поэтому петлю держит свой счёт:
   больше `MAX_LOOPS` возвратов подряд без владельца → `waiting`, причина
   «роли гоняют задачу по кругу», те же три кнопки.

«Артефакт на месте» = файл существует, не пустой, первый заголовок `## Итог`
или `## Для владельца`. Больше движок в содержание не смотрит.

**Кнопки владельца** (только из панели, только с текущей ревизией):
Принять → `next` (или выбранный исход), Вернуть на X (из `moves`), Вернуть на
X начисто, Продолжай, Ещё заход, Принять как готово/как есть, Запустить (из
бэклога и очереди).

«Вернуть на X» — доводка: шаг с `context: own` продолжит свою прошлую
сессию, файлы шагов ниже останутся в `artifacts/` и уедут в их промпты.
«Начисто» — переигранное решение: всё, что задача сделала с последнего
захода в X, забывается. Заходы помечаются `run.void_at` (строки остаются:
путь задачи по шагам задним числом не переписывают), их сессии больше не
подхватываются `own`/`continue`, предел заходов считается заново, а
артефакты шагов ниже уезжают в `history/cleared-<время>/`. Свой артефакт
шага X остаётся: роль перепишет его сама, а соседям он нужен как основание.
Без этого план после переигранного Решения читал старое `plan-review.md`,
считал ревью пройденным и уходил на ворота (T26).
Текст из поля ввода в момент нажатия — комментарий движения; адресат всегда
та роль, чей ход запускает кнопка (при «Продолжай» — та же роль). Запись
`move(actor: human, trigger: button, comment)` + `status: running`. Если у
задачи есть открытый заход (сессия в ошибке, воркер не поднялся), кнопка
сначала закрывает его без исхода: иначе движок продолжал бы следить за
мёртвой сессией, и «Ещё заход» ничего бы не заводил.
Если владелец правил артефакт руками между сигналом роли и кнопкой
(отпечаток файла изменился), блок задачи следующей роли получает строку
«файл `plan.md` правил владелец после сдачи».

**Завершение.** `next: done` → `status: done`, цвет `green`, `closed_at`.
Через 168 ч — архив всех сессий задачи (`archived_at`). Сессии никогда не
удаляются движком.

## 6. Команда `orch` для ролей

Работает из рабочей копии задачи, читает только `.orch/<task>/`:

- `orch done [<исход>]` — проверяет по `chain.yml`: исход допустим для
  шага из `current.json`, артефакты `artifact` существуют, не пусты и
  начинаются с нужного заголовка; печатает ошибку с подсказкой (код 1) или
  пишет `signals/<step>-<n>.json` атомарно (tmp + rename). Повторный вызов
  на уже сданный заход — ошибка «ход уже сдан». После второго отказа за
  заход команда добавляет: «дальше не повторяй: запиши в `## Не решено`,
  чего не хватает, и закончи ход без сигнала» — и пишет отказ в
  `signals/` как `refused`, чтобы панель показала текст.
- `orch whoami` — задача, шаг, заход, файлы для чтения.
- `orch note "<текст>"` — запасной канал комментария.
- `orch push` — пушит только ветку задачи, без `--force`; роли не пушат
  иначе. Git-хуки не ставим: у worktree они общие с основным репозиторием.
- `orch gate accept | back <шаг> | again [--comment "…"]` — решение
  владельца, сказанное словами в чате, а не кнопкой в панели. Работает
  только когда задача действительно ждёт владельца (`UX-PLAN.md`).
- `orch task new --backlog --chain <имя> --project <корень> "<текст>"` —
  заявка в `inbox/`, движок создаёт задачу на следующем проходе. Пользуются
  Разведка (разбиение) и PR (долг).
- `orch task start <T> --chain <имя> --preset <имя>` — отпустить заявку из
  бэклога в работу. Едет она сама: номер, ветка и строка в журнале остаются
  её, от бэклога до PR. Названное заменяет записанное в заявке, неназванное
  остаётся как было.

Роль обязана закончить ход вызовом `orch done` — последнее действие хода.

Для человека: `orch task list|show|new|start|move|note`, `orch log <task> --follow`
(журнал `event` живьём), `orch stats [--last N]` (по шагам: заходов на
задачу, доля «нет сигнала», медиана длительности хода, вопросов владельцу —
сигнал регресса после правки промпта), `orch wizard <project>`,
`orch chains`, `orch branches`, `orch task edit`, `orch doctor`.

## 7. Сборка промпта

Чистая функция (цепочка, шаг, состояние задачи, файлы) → текст, сохраняется
в `prompts/` до отправки, хеш в `run.prompt_sha`. Порядок блоков:

1. `includes` цепочки.
2. Промпт роли `prompt.file`.
3. `prompt.instructions`.
4. **Задача**: «Исходная постановка целиком, не твоя инструкция; что делать
   тебе — ниже» + текст.
5. **Где ты**: путь задачи с циклами
   (`Разведка → Решение → План → Ревью плана ⟲ План → [ты: Ревью плана, заход 2]`);
   одна из трёх фраз, откуда пришла: «вернул владелец с комментарием»,
   «вернула роль X исходом Y», «владелец нажал „ещё заход“ / „продолжай“»;
   номер захода; предел заходов, если это последний допустимый.
6. **Файлы**: `prompt.reads` с путями; каких из них нет — отдельной строкой;
   свой прошлый файл, если заход > 1 («перепиши, новый не заводи»);
   «изменилось после твоего прошлого захода» — `git diff --stat <end_sha
   прошлого захода>..HEAD` и артефакты с более поздним временем; строка о
   правке владельцем, если была. Путь к папке навыков, пути к `sub-*.md`
   для шага с подагентами.
7. **Комментарии владельца** — из `move.comment` движений в этот шаг после
   прошлого захода этого шага, дословно.
8. **Вопросы**: «вопросы владельцу задавать можно / нельзя (реши сам,
   запиши выбор в `## Допущения`)» по листу автономии.
9. **Завершение**: «последнее действие хода — `orch done <исход>`; исходы:
   …; артефакт: …; после остановки правки владельца вноси в свой файл».

Из чужих артефактов в блок задачи попадают только пути и раздел `## Итог`,
никогда произвольный текст. Собранный промпт больше 60k токенов — событие
и `reads` вклеиваются путями без содержания.

## 8. Интерфейс (плагин AoE)

Манифест `orch/aoe-plugin.toml`, `api_version 13`, capabilities:
`runtime.worker`, `session.read`, `composer.read`, `composer.write`,
`notifications`. Слоты:

- **`home-pane` «Задачи»**: секции «Ждут вас» (причина, время ожидания,
  старшие сверху, кнопки), «Бэклог» (строка на заявку, кнопки «В работу» /
  «Править ТЗ» / «Удалить»; «В работу» отпускает саму заявку — номер задачи
  не меняется от бэклога до PR), «Новая задача» (строка на проект → мастер в
  чате; «в бэклог» — записать без вопросов). Едущих, очереди, готовых и
  снятых на обзоре нет: см. `UX-PLAN.md`.
- **`pane` задачи** (в любой сессии задачи): путь шагов, текущий шаг и
  сессия, «Ждёт: причина», последний ответ `orch`, время в состоянии,
  кнопки по причине, лист автономии для непройденных шагов, ссылки на
  артефакты (`GET /api/sessions/{id}/file`), последние комментарии, журнал
  10 событий, предупреждение о дорогом ходе.
- **`row-badge` на строке сессии**: зачем строка зовёт — ворота, вопрос,
  нет сигнала, какой шаг из скольких. Подсветку строки хост даёт сам по
  `urgent` (`UX-PLAN.md`).
- Настройки плагина (рисует AoE): интервал опроса (5 с), `max_running` (3),
  порог предупреждения о стоимости хода ($5), цепочка по умолчанию.

Панели — функция состояния; перерисовка при смене ревизии. Кнопки несут
`{task, revision, action, target}`. Пуши — штатные AoE: `notify_on_idle`
включается у сессии шага с воротами по листу; `urgent` на остановках.

**Сессия мастера** — по одной на проект, открывает движок по кнопке «Новая
задача» или «В работу» (или `orch wizard <project>`): структурная сессия
Claude (sonnet) с промптом `prompts/role-wizard.md`. Мастер доводит мысль
владельца до текста задачи фиксированной формы, спрашивает вариантами
цепочку, ветку и автономию и сам заводит задачу вызовом `orch task new` —
а заявку из бэклога не заводит заново, а отпускает (`orch task start <T>`).
Так заведение задачи не упирается в панель, где нет ни полей ввода, ни
выпадающих списков (`UX-PLAN.md`).

Сайдбар: ось **«по группе»** (её и держит владелец), группа на задачу и
называется `<проект>/<T12> · <титул>` — проект первым, чтобы задачи одного
проекта вставали рядом при сортировке групп по имени; мастер — `<проект>/
мастер`. Титул сессии шага = `T12 · <шаг>`, цвет `amber`/`red`/`green`.
Сессии пройденных шагов остаются до архива и видны каждая своей строкой —
ради этого сессии и создаются без `worktree_*` (см. §5, «Старт»).

Строка побочной роли стоит в той же группе, но её сессия живёт в другом
каталоге (Наладчик — в живом дереве `vps-dev`), поэтому на оси «репо и
группа» она отваливается в секцию своего репозитория. Чтобы её было видно
среди строк шагов: знак роли в титуле (`icon` в описании роли, у Наладчика
`🔧`, титул `🔧 T35 · Наладчик`) и свой бейдж на строке. Стенд помечен так
же (`🧪 T35 · стенд`): служебные сессии видно среди рабочих — имя роли, а во время хода повод.

## 9. Вызовы AoE

| Действие | Вызов |
|---|---|
| статусы всех сессий | `GET /api/sessions?state=live` |
| создать сессию | `POST /api/sessions?wait=ready` {path, tool, title, group, view: structured, agent_name, agent_model, agent_effort, yolo_mode: true, worktree_*, idempotency_key} |
| промпт | `POST /api/sessions/{id}/acp/prompt` {text} → disposition |
| отменить ход | `POST /api/sessions/{id}/acp/cancel` |
| сменить модель | `POST /api/sessions/{id}/acp/config-option` |
| титул / группа / цвет / уведомления | `PATCH /api/sessions/{id}`, `/group`, `/color`, `/notifications` |
| срочно | файл `/tmp/aoe-hooks-<uid>/<id>/attention.json` `{"urgent": true}` |
| архив | `POST /api/sessions/{id}/archive` |
| ссылки на файлы | `GET /api/sessions/{id}/file?path=` |
| стоимость и длительность хода | события `UsageUpdated` из `GET .../acp/replay` после `Idle`; только Claude сообщает цену |

Режим полных прав: карта `claude → bypassPermissions`,
`codex → agent-full-access`, `opencode → …`; через `yolo_mode: true` при
создании, при отказе адаптера — предупреждение в журнал.

## 10. Этапы и критерии готовности

**0. Спайк** (см. `RISKS.md`, шесть проверок). Готово: каждая проверка —
скрипт в `orch/spike/` с выводом «ok/fail» и записью результата в
`RISKS.md`.

**1. Ядро без панели.** Пакет, база с миграциями, линтер цепочек, сборка
промпта, клиент AoE, reconcile, `orch` CLI (task new/list/show/move,
done/ask/whoami/note/push, log, stats, doctor). Цепочка `smoke`
(`chains/smoke.yml`, `prompts/test-smoke-*.md`) проходит на
`/projects/kandev-trial` с листом по умолчанию и с выключенными воротами, с
возвратом, с «нет сигнала», с выключенными вопросами. Юнит-тесты движка
против поддельного AoE зелёные.

**2. Панель.** Плагин установлен, `home-pane`, `pane`, `row-badge`,
лист автономии; `smoke` проходится целиком с телефона: создание, ворота,
комментарий, возврат, приёмка, правка листа по ходу.

**3. Conventions.** Промпты и цепочка готовы (`prompts/role-conventions*.md`,
`chains/conventions.yml`). Conventions проходит с воротами и без на
полигоне. Каждое место, где роль споткнулась о промпт (не поняла блок задачи,
не вызвала `orch done`, назвала не тот исход, не нашла файл), записывается в
`orch/PROMPT-NOTES.md` и правится в промпте тут же.

**4. Deep.** Восемь шагов готовы (`chains/deep.yml`, `prompts/role-*.md`,
`sub-*.md`). Сначала одна маленькая задача на полигоне `kandev-trial` (одна
развилка, тест, документ; заложены автовозврат ревью плана и возврат
владельца с комментарием). Затем **настоящая задача** — авторизация в
`/projects/listate-crm` по `FIRST-TASK.md`: разработчик играет владельца,
доводит задачу до PR, сравнивает с ожиданиями, пишет `FIRST-TASK-REPORT.md`.
Надзор за промптами на обеих. Сравнение с прогоном Kandev от 2026-09-04
(`kandev/research/TRIAL-2026-09-04.md` в истории git: каталог снят вместе
с доской).

**5. Выкатка.** Роль Ansible `orch`: venv, `pip install -e`,
`aoe plugin install`, `rate_limit_auto_resume = true`, `smart_rename = true`,
бэкап базы вместе с `~/.config/agent-of-empires`.

## 11. Тесты

- **Движок**: чистые функции + поддельный AoE в памяти. Сценарии: прямой
  путь; возврат до `max_runs`; нет сигнала; кнопки с устаревшей ревизией;
  сигнал и кнопка одновременно; Stop после сигнала; падение между
  транзакцией и созданием сессии; четыре состояния сессии после рестарта;
  сессия исчезла; лист автономии: ворота по исходу, выключенные вопросы →
  отмена и промпт; очередь `max_running`; правка артефакта владельцем.
- **Линтер**: все `chains/*.yml` в CI; отрицательные файлы на каждую ошибку;
  пресеты.
- **Промпт**: снимки для первого захода, второго после возврата владельца,
  второго после возврата роли, `continue`, выключенных вопросов,
  отсутствующего файла из `reads`.
- **`orch`**: неверный исход, нет артефакта, не тот заголовок, вне задачи,
  повторный `done`, третий отказ.
- **Интеграция** (метка `live`, против живого AoE): спайк + `smoke`.

## 12. Отложено

`mode: plan`, `context: fork`, `reads` с проверкой движком, `skip_if`,
пределы времени и стоимости (есть только предупреждение), параллельные
шаги и WIP по шагам, хуки до/после, запасной агент, бейджи в сайдбаре,
маршруты Quick/Standard, `on_done`, таймер авто-принятия ворот, интерфейс
настроек цепочек, мульти-репо.
